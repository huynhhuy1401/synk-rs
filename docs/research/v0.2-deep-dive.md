## TL;DR

1. **On small corpora, the number of test documents decides everything.**
   With per-document changes that spread about ±0.10 (a guess; measure it),
   a test needs about **34 test documents** to catch a typical +0.05 gain 8
   times out of 10, and **10** to catch a +0.10 gain. Today, 11 documents
   give 1–2 test documents, and nothing warns you before training. For
   v0.2: show `test_documents` in the dry run, warn there
   (`TEST_SET_UNDERPOWERED`), make `--sample` keep every test document, and
   add `test_percent = "auto"` (at least 10 test documents, at most half).
   Leave cross-validation over documents (`eval.folds`) to v0.3: it is the
   real fix, but it costs K trainings and needs careful labelling.
2. **The sign-flip (permutation) test cannot say anything with 5 or fewer
   test documents**: its smallest possible p-value is 2/2⁵ = 0.0625. From 8
   documents on, it is as strong as the t-test in my simulation. Report it
   next to the t-test as a cross-check; don't make it the rule.
3. **Real queries are the cheapest honest fix.** Add `synk queries template`
   (one line per document; you write how you'd search for it *without
   opening it*), skip the lines you leave empty on import, and let real
   queries decide the verdict only when they cover 10 or more documents.
   Today 30 real queries from 2 documents take over the verdict
   (`train.rs:623`) and almost always produce "no clear change".
4. **GGUF export: ship the converter inside synk instead of downloading
   it.** The files synk needs are about 2 MB of MIT-licensed Python
   (measured), but today it downloads the whole llama.cpp repository
   (178 MB uncompressed) from GitHub with no consent item
   (`synk_sidecar.py:902-933`). The pinned commit is already compiled into
   the binary (`export.rs:24`), so vendoring adds no extra update burden.
5. **Ctrl-C: replace the 120 s heartbeat guess with an OS file lock.** A
   lock that the operating system releases when the process dies
   (`File::try_lock`, stable since Rust 1.89) fixes both the lock race and
   the "still running for 120 s" problem. Catch Ctrl-C with the `ctrlc`
   crate. The first press stops at the next safe point and saves a
   checkpoint. The second press stops at once. Run the Python trainer in
   its own process group, so the terminal's Ctrl-C doesn't kill it
   mid-save, and give it a "lifeline" pipe so it stops when synk dies.
   Finding: today, Ctrl-C hits **both** synk and Python. Python raises
   `KeyboardInterrupt`, which the sidecar's `except Exception` doesn't catch
   (`synk_sidecar.py:1082`). So the "save a checkpoint, then stop" path
   never runs on Ctrl-C.
6. **Disk space: the error code `INSUFFICIENT_DISK` already exists, but
   nothing raises it** (`error.rs:44,118,206`, and README's error table
   leaves it out). Raise it as a dry-run blocker when a volume can't fit
   what the steps need. A full fine-tune of e5-small needs roughly 3–4 GB
   at its peak in `.synk/artifacts` **[estimate]**. Use `fs4::available_space`.
7. **Vietnamese: NFC normalization changes how synk reads text.** Text in
   decomposed form (NFD) is detected as *Latvian* by whatlang (measured),
   and mixed vi/en lines are often detected as English, French, Latin or
   Catalan. A cheap rule, "2% or more of the letters are ă, đ, ơ, ư or in
   U+1EA0–U+1EF9 → Vietnamese", fixed 3 of 4 mixed test lines and left
   French alone.
8. **Export snippets, checked against source code:** LlamaIndex *removes*
   the model's prefixes for a local folder unless you pass
   `query_instruction`/`text_instruction`. LangChain needs
   `query_encode_kwargs={"prompt_name": "query"}`. Open WebUI applies
   `RAG_EMBEDDING_QUERY_PREFIX` / `RAG_EMBEDDING_CONTENT_PREFIX` with both
   its built-in engine and the Ollama engine. AnythingLLM's Ollama embedder
   sends text as is, with no prefix setting.
9. **Two "fixes" from the survey need changing.** Adding `--exclude-newer`
   to the torch install step as it stands *breaks* the install (tested).
   NFC needs a "reader version", because unchanged files are never re-read
   (`fs.rs:131`).

## Part 0. The ideas behind the verdict, in plain words

You need these to follow chapter A. Each idea comes with a small example.

### 0.1 What synk measures: nDCG@10, per query

For each test query, synk knows which chunk should come first. It asks each
model to rank every chunk, then looks at where the right chunk landed:

| Rank of the right chunk | Score (nDCG@10) |
|---|---|
| 1 | 1.00 |
| 2 | 0.63 |
| 3 | 0.50 |
| 4 | 0.43 |
| 10 | 0.29 |
| 11 or worse | 0 |

(`train.rs:548-554`: 1 / log₂(rank + 1), and zero after rank 10.)

### 0.2 Why the unit is a document, not a query

Example: the document `nginx.md` has 4 test queries.

| Query | Base rank → score | Tuned rank → score |
|---|---|---|
| tăng timeout nginx | 1 → 1.00 | 1 → 1.00 |
| nginx 504 gateway | 3 → 0.50 | 1 → 1.00 |
| keepalive bao lâu | 2 → 0.63 | 2 → 0.63 |
| reload không mất kết nối | 12 → 0 | 4 → 0.43 |
| **mean** | **0.53** | **0.77** |

The document's **change** is +0.23. The 4 queries share one text, so they
tend to succeed or fail together. Counting them as 4 independent pieces of
evidence would be like asking one person the same question four times and
calling it a survey. So synk averages them into one number per document
(`train.rs:667-676`), and the test works on those numbers.

### 0.3 The paired t-test and the 95% interval

With 5 test documents, the per-document changes might be:

```
+0.12  +0.05  -0.02  +0.08  +0.10      mean +0.066, spread (sd) 0.055
```

The t-test asks: "if tuning truly did nothing, how surprising is a mean
of +0.066 with this much spread, from only 5 numbers?" It produces:

- a **95% interval** for the true change: here **−0.002 to +0.134**;
- a **p-value**: here **0.054**.

synk says `better` only when the whole interval is above zero
(`train.rs:678-682`). Here it starts just below zero, so the verdict is
**no clear change**, even though 4 of 5 documents improved. That is not a
bug. Five numbers just can't rule out "no effect".

Same kind of gains, but 11 test documents:

```
+0.12 +0.05 -0.02 +0.08 +0.10 +0.07 +0.03 +0.09 -0.01 +0.06 +0.04
mean +0.055, sd 0.044 → 95% interval +0.026 to +0.085, p = 0.002 → better
```

(Both computed with SciPy; see [A.2](#a2-the-power-table).)

### 0.4 Power and the smallest detectable change

- **Power**: if tuning truly improves search by X, how often would the
  test say `better`? 80% is the usual target. Power below 50% means the
  test usually misses a real gain.
- **Smallest detectable change** (synk's `min_detectable_delta`,
  `stats.rs:49`): the true gain the test would catch 80% of the time. If it
  is 0.17 and typical gains are 0.05, the test is too small to see a
  typical gain.

Power depends on three things only:

1. the **number of test documents** (more is better);
2. the **spread** of per-document changes (sd; less is better);
3. the **size of the true gain** (bigger is easier to see).

You can't control the gain, and the spread is mostly fixed by your data.
**The number of test documents is the one lever synk has.**

### 0.5 The sign-flip (permutation) test, in one example

A different way to get a p-value, with no assumption that the numbers
follow a bell curve. If tuning did nothing, each document's change is as
likely to be +x as −x. So: flip the signs in every possible way, and count
how often the flipped mean is at least as far from zero as the real one.

With 3 documents there are 2³ = 8 ways to flip. Even if the real mean is
the most extreme of all 8, the two-sided p-value is 2/8 = 0.25. **With n
documents the smallest possible p-value is 2/2ⁿ**: 0.0625 at n = 5,
0.031 at n = 6, 0.0078 at n = 8. So with 5 or fewer documents this test can
*never* reach 0.05. That is an honest summary of how little 5 documents can
show.

## A. Verdict power on small corpora

### A.1 The problem, simply

The Kaggle run had 11 documents. With `test_percent = 20`, the hash split
held out 1 of them. One document gives one number. You can't draw an
interval through one number, so the verdict was "too few to tell" before
training even started (`stats.rs:22-26`, `train.rs:712-716`). Nothing in the
dry run said so.

### A.2 The power table

Two-sided test at 0.05, power by exact integration over the t distribution
(SciPy). In brackets: what synk's own formula `(t₀.₉₇₅ + t₀.₈₀) × sd / √n`
(`stats.rs:49`) gives. The two agree closely from n = 4 on, so the code's
formula is fine.

**Smallest change seen 80% of the time**, by test documents (n) and spread
(sd) of per-document changes:

| n | sd 0.05 | sd 0.10 | sd 0.15 | sd 0.20 |
|---|---|---|---|---|
| 2 | 0.58 (0.50) | 1.15 (1.00) | 1.73 | 2.31 |
| 3 | 0.16 | 0.33 (0.31) | 0.49 | 0.65 |
| 4 | 0.11 | 0.21 | 0.32 | 0.43 |
| 5 | 0.084 | 0.17 | 0.25 | 0.34 |
| 6 | 0.072 | 0.14 | 0.21 | 0.29 |
| 8 | 0.058 | 0.12 | 0.17 | 0.23 |
| 10 | 0.050 | 0.10 | 0.15 | 0.20 |
| 12 | 0.044 | 0.089 | 0.13 | 0.18 |
| 15 | 0.039 | 0.078 | 0.12 | 0.16 |
| 20 | 0.033 | 0.066 | 0.099 | 0.13 |
| 30 | 0.026 | 0.053 | 0.079 | 0.11 |
| 50 | 0.020 | 0.040 | 0.061 | 0.081 |

nDCG changes can't exceed 1, so the n = 2 row means "impossible".

**Chance of seeing a true +0.05 gain** (power):

| n | sd 0.05 | sd 0.10 | sd 0.15 | sd 0.20 |
|---|---|---|---|---|
| 3 | 18% | 8% | 7% | 6% |
| 5 | 40% | 14% | 9% | 7% |
| 10 | 80% | 29% | 16% | 11% |
| 15 | 95% | 44% | 23% | 15% |
| 20 | 99% | 56% | 29% | 19% |
| 30 | 100% | 75% | 42% | 26% |
| 50 | 100% | 93% | 64% | 41% |

**Chance of seeing a true +0.10 gain:**

| n | sd 0.05 | sd 0.10 | sd 0.15 | sd 0.20 |
|---|---|---|---|---|
| 3 | 47% | 18% | 11% | 8% |
| 5 | 91% | 40% | 21% | 14% |
| 10 | 100% | 80% | 47% | 29% |
| 20 | 100% | 99% | 81% | 56% |
| 30 | 100% | 100% | 94% | 75% |

**Test documents needed for 80% power:**

| True gain | sd 0.05 | sd 0.10 | sd 0.15 | sd 0.20 |
|---|---|---|---|---|
| +0.03 | 24 | 90 | 199 | 351 |
| +0.05 | 10 | 34 | 73 | 128 |
| +0.10 | 5 | 10 | 20 | 34 |

Which sd is realistic? **Unknown [unverified]**. It depends on how many
queries each document has (more queries average out noise) and on how
uneven the gain is across documents. The first real runs should record it.
synk already has every number it needs (`per_query.jsonl`). The design
below uses the sd of the project's last evaluation when there is one, and
0.10 otherwise, and says which it used.

How the hash split falls at `test_percent = 20` (binomial, N documents):

| Documents | Mean test docs | Chance of ≤ 2 test docs | Chance of < 5 |
|---|---|---|---|
| 6 | 1.2 | 90% | ~100% |
| 11 | 2.2 | 62% | 95% |
| 20 | 4 | 21% | 63% |
| 30 | 6 | 4% | 26% |
| 50 | 10 | 0.1% | 2% |

**Conclusion**: below ~50 documents, the 20% hash split gives a test that
can only see large gains. Below ~20 documents, it can barely see anything.

### A.3 What synk does today

- Split: whole documents, by a hash of the path within the source, bucket
  0–9999 below `test_percent × 100` → test (`dataset.rs:749-772`). If one
  side is empty, one document is moved (`dataset.rs:773-787`).
  `test_percent` is a `u8` (`config.rs:176`).
- `--sample N` / `max_chunks` samples **chunks**: it keeps the train/test
  share of chunks and takes the first N of each split by chunk ID
  (`dataset.rs:543-560`). Test chunks belong to few documents, so the
  sample can drop whole test documents.
- The dry-run plan counts `test_chunks` (`dataset.rs:605`,
  `graph.rs:737-744`), not test documents. The dry-run output has no
  advice at all (`work.rs:608-641`).
- `TEST_SET_UNDERPOWERED` fires only after evaluation, when the 95%
  interval's half-width is over 0.05 (`advice.rs:248-268`). Its action is
  "add documents".
- The verdict is a paired t-test on per-document means (`train.rs:661-737`,
  `stats.rs:22-51`). No permutation test.
- With fewer than 20 training documents there is no dev split, so no
  over-fitting check for `epochs = "auto"` (`synk_sidecar.py:386-394`).

### A.4 Options

**A-1. Warn in the dry run (cheap, must).** Count test documents in the
plan, predict the smallest detectable change, warn. This spends no time.

**A-2. `test_percent = "auto"` (cheap).** Hold out more documents on small
corpora. Cost: fewer training documents, so a weaker model. Stability rules
below.

**A-3. `--sample` keeps every test document (cheap, must).** Sample
training chunks freely, but cap the chunks *per test document* instead of
taking the first N test chunks.

**A-4. Cross-validation over documents, `eval.folds = K` (medium).** Split
the documents into K groups ("folds"). Train K models; each one leaves out
one fold and is tested on it. Every document gets tested exactly once, by a
model that never saw it. 11 documents → n = 11 instead of n = 1.

**A-5. Sign-flip p-value as a cross-check (cheap).**

**A-6. Refit on all documents before export (medium, after A-4).**

They don't compete. They stack: A-1, A-3 and A-5 are cheap and change no
existing verdicts; A-2 changes splits; A-4 and A-6 change what a "run" is.

#### A-2 in detail: how "auto" picks test documents, and why stability matters

A first idea, "hold out 40% when the corpus is small", fails in a subtle
way. A percentage threshold on the hash keeps each document's side fixed
only while the percentage stays the same. A rule that changes the
percentage with corpus size moves documents across the line whenever the
corpus grows.

Why stability matters even though one run never leaks (its split is
computed once):

- `synk run compare` across datasets is only fair when the test documents
  overlap.
- A document that bounces between train and test on every edit confuses
  people ("why is my nginx note in the test this time?").
- A stable rule keeps large projects' datasets **identical to today's**
  (same keys, no retraining).

**Proposed rule ("threshold, then top up"):**

1. Start from today's split: bucket < 2000 (20%) → test.
2. Let `target = min(10, floor(N / 2))`. If the test has fewer than
   `target` documents, move training documents into the test **in order of
   smallest bucket** until it has `target`.
3. Never move documents the other way.

| Documents N | 20% split (expected) | auto target | Test docs (auto) | Training docs left |
|---|---|---|---|---|
| 2 | 0–1 | 1 | 1 | 1 |
| 6 | ~1.2 | 3 | 3 | 3 |
| 11 | ~2.2 | 5 | 5 | 6 |
| 20 | ~4 | 10 | 10 | 10 |
| 30 | ~6 | 10 | 10 | 20 |
| 50 | ~10 | 10 | ≥10 | ≤40 |
| 150 | ~30 | 10 | ~30 (no top-up) | ~120 |

Properties:

- For big corpora (where the 20% split already gives ≥ 10 test documents)
  the split is **exactly today's**. Record `min_test_documents` in the
  dataset params **only when the top-up moved something**, so those keys
  stay the same.
- For a fixed corpus the split is deterministic.
- When documents are added, a former top-up document can return to
  training (when a new document has a smaller bucket, or when the 20% split
  alone reaches the target). That only happens when the corpus changes.
  Say so in GLOSSARY.
- The cost is real. On 11 documents, auto trains on 6 documents instead of
  10, and the model gets worse. `FEW_QUERIES` / `FEW_TRAINING_STEPS` will
  fire more often. That is the honest trade-off until folds exist.

#### A-3 in detail: sampling per test document

Today: `test_n` = the test share of `max` chunks, then the first `test_n`
test chunks by chunk ID (`dataset.rs:550-556`). Chunk IDs are hashes, so
the first 20 test chunks may all come from 2 documents.

Proposed: `per_doc = max(1, ceil(test_n / test_docs))`, take up to
`per_doc` chunks from **each** test document (first by chunk ID, so it
stays stable), then fill the rest of `max` with training chunks. If
`max < test_docs + 2`, raise `max` to `test_docs + 2` and say so in the dry
run (`"sample_raised_to": 14`). Add `"sample": "per_test_document"` to the
dataset params **only when `max_chunks` is set**, so unsampled datasets keep
their keys.

Example: `--sample 60` on 30 documents, 6 of them test with 40 test chunks
in all. Today: 60 × 40/200 = 12 test chunks, which may come from only 3
documents. Proposed: 2 chunks from each of the 6 test documents, plus 48
training chunks. The LLM bill is the same, and the test is twice as large
in the unit that counts.

#### A-4 in detail: cross-validation over documents

**How it works, with 11 documents and K = 5:**

```
docs sorted by hash bucket, dealt round-robin into 5 folds:
fold 1: d03 d08 d11     fold 2: d01 d06     fold 3: d04 d09
fold 4: d02 d07         fold 5: d05 d10

model 1 trains on folds 2–5, is tested on fold 1 → changes for d03, d08, d11
model 2 trains on folds 1,3–5, tested on fold 2  → changes for d01, d06
...
pool: 11 per-document changes → one paired test, n = 11
```

**How the verdict is computed.** Exactly as today. `judge()` already pools
by document (`train.rs:667-676`). Each fold's eval writes its
`per_query.jsonl` rows. Concatenate them, and each document appears once.

**Caveats (say them out loud):**

1. The K models share most of their training data, so the per-document
   changes are not fully independent. Bengio & Grandvalet prove that "there
   exists no universal (valid under all distributions) unbiased estimator
   of the variance" of K-fold cross-validation
   ([JMLR 2004](https://www.jmlr.org/papers/v5/grandvalet04a.html)). In
   practice the naive interval tends to be too narrow (too optimistic).
   Nadeau & Bengio propose a corrected variance for resampled tests
   ([Machine Learning 52, 2003](https://doi.org/10.1023/A:1024068626366))
   **[I could not open the paper to check how it applies here, unverified]**.
   How large the effect is for synk is **[unverified]**. Measure it on the
   benchmark (survey §4.3).
2. The verdict is about **the recipe on your documents** ("tuning
   e5-small this way helps on corpora like yours"), not about one saved
   model. No single fold model was tested on all documents.
3. The training randomness of each fold is not in the interval either. A
   second seed could move the result.

**What do you export?** Options:

| Option | Honest? | Quality |
|---|---|---|
| The best fold model | No: picking the winner after looking inflates it ("winner's curse") | Trained on 80% |
| An average of fold models' weights | Untested for this; unusual **[unverified]** | Unknown |
| **A refit on all documents** (K+1th training) | Yes, if labelled "recipe verified by 5-fold CV; this model trained on everything, so no held-out score exists for it" | Trained on 100% |

Recommend the refit, and make it part of the run (one more train step), so
`synk export` exports it as usual.

**Cost.** K + 1 trainings. On a CPU, e5-small takes ~13 min per training
(README estimate), so K = 5 is ~80 min. On a T4, ~190 s per training (Kaggle
field notes) → ~20 min. LLM time is unchanged: queries are cached per chunk,
and every chunk already gets queries today.

**Caching.** Each fold is its own train artifact, keyed by the dataset,
the params and `"fold": "2/5"`. The refit is keyed `"fold": "all"`. An
interrupted CV run resumes at the fold where it stopped. Changing one
document changes the dataset key, so all folds retrain (as today, where any
document change retrains).

**Data format.** `corpus.jsonl` gains `fold` (an integer, 1..K), a new
field, which JSONL `v` rules allow. `split` stays, so old readers keep
working. The sidecar `train`/`eval` requests gain `"fold": k` (train on
`fold != k`, test on `fold == k`). That is an added field in protocol v2.
The script is embedded and content-hashed (`sidecar.rs:292-299`), so the
binary and the script always match.

**Real queries under CV.** Real queries were never trained on. Evaluate
them with the refit model against the base, over the whole corpus, exactly
like today (`synk_sidecar.py:752-754`).

#### A-5 in detail: the sign-flip test

Exact enumeration for n ≤ 20 (2²⁰ ≈ 1M sign patterns × n additions, well
under a second in Rust). Above 20, the t-test is reliable and the sign-flip
p adds little: report `null`, or use a fixed-seed Monte Carlo with 100,000
draws.

Simulation (2,000 runs, true gain +0.05, sd 0.10, normal changes): share
of runs that said `better`:

| n | t-test | sign-flip |
|---|---|---|
| 5 | 13% | **0%** |
| 6 | 17% | 11% |
| 8 | 22% | 20% |
| 10 | 28% | 28% |
| 15 | 44% | 43% |
| 20 | 55% | 55% |

So from 8 documents on they agree. Below that, the sign-flip test shows how
much of a `better` rests on the bell-curve assumption alone. In IR
evaluation, the t-test, bootstrap and randomization tests agree closely at
normal topic counts
([Smucker, Allan & Carterette, CIKM 2007](https://ciir-publications.cs.umass.edu/getpdf.php?id=744)).
**Keep the t-test as the decision rule**, so verdicts don't change meaning.
Add `permutation_p` to the verdict, and add a sentence when the two
disagree.

#### A-6 in detail: refit before export (holdout runs)

For a non-CV run: `synk export run:3 --refit` trains once more on train +
test documents, with run 3's settings and run 3's chosen epoch count
(`best_epoch`). The verdict stays the one measured on run 3's held-out
documents, and the export says so. This is a weaker promise, so it must be
opt-in and labelled. It is cheaper to do inside CV (A-4) first.

### A.5 Recommended design

**v0.2 (must): A-1, A-3. Should: A-2 (as the default, see Decision 1), A-5.
v0.3: A-4 with its refit, then A-6 for holdout runs.**

**Dry-run JSON** (`synk train --dry-run --json`): the dataset step's
`detail` gains `train_documents` and `test_documents`
(`graph.rs:737-744`). `data.advice` is a new, add-only field:

```json
{"v": 1, "ok": true, "data": {
  "would": "a new run",
  "steps": [ ..., {"step": "dataset", "action": "run",
     "detail": {"chunks": 41, "train_chunks": 35, "test_chunks": 6,
                "train_documents": 9, "test_documents": 2, "llm_calls": 41}} ],
  "advice": [{
    "code": "TEST_SET_UNDERPOWERED",
    "severity": "warning",
    "message": "Only 2 of 11 documents are held out for the test. A test this small can only see changes of about 1.15 or more in search quality (assuming per-document changes spread about 0.10), so the verdict will almost surely be 'no clear change', even if tuning helps. Hold out more documents (dataset.test_percent = \"auto\"), or write 30 real searches over 10+ documents (synk queries template).",
    "evidence": {"predicted": true, "test_documents": 2, "documents": 11,
                 "assumed_sd": 0.10, "sd_source": "default",
                 "min_detectable_delta": 1.15, "power_at_0_05": 0.06},
    "action": {"command": "synk train --dry-run",
               "config": {"dataset.test_percent": "auto"}},
    "applicability": "review"
  }]
}}
```

Notes:

- **Same code, new trigger.** `TEST_SET_UNDERPOWERED` keeps its meaning
  ("the test is too small to see small changes"). The dry-run version
  carries `evidence.predicted: true`. Agents that already handle the code
  need no change.
- `applicability: "review"`, not `machine`: it changes the result (fewer
  training documents).
- Trigger: predicted `test_documents < 10` and no real-query set that will
  decide (B). Below 3 test documents, say "can't give a verdict at all".
- `assumed_sd`: the sd of per-document changes from this project's latest
  evaluation (`sd_source: "run:3"`), or 0.10 (`"default"`).
- Human dry-run line: `run dataset 41 chunks (2 test documents); ...`, then
  the advice message under the steps.

**Config** (`synk.toml`):

```toml
[dataset]
test_percent = "auto"   # or a number, as today; "auto" = 20%, topped up to at least 10 test documents (at most half)
```

`test_percent` becomes `AutoOr<u8>` (`config.rs:56-117` already does this
for other keys). `"auto"` serializes as `"auto"`, numbers as numbers, so
existing files and `--set dataset.test_percent=30` keep working.

**Verdict JSON** (add-only):

```json
"verdict": {
  "outcome": "no_clear_change", "p_value": 0.054,
  "permutation_p": 0.125, "permutation_exact": true,
  "method": "holdout",
  "message": "No clear difference ... (+0.066, 95% CI -0.002 to +0.134) on 19 test queries from 5 documents. This test set can only detect changes of about 0.168 or more. With 5 documents, an exact sign-flip test can't reach p < 0.05 at all."
}
```

`method` is `"holdout"` now and `"cross_validation"` later (v0.3, with
`"folds": 5`).

**v0.3 config, for reference:** `[eval] folds = 5` (0 or 1 = off). New
advice `USE_FOLDS` (review) when predicted test documents < 8 and
documents ≥ 6.

**KIND_VERSION.** A-3 and A-2 change the dataset output only where the new
params appear (`sample`, `min_test_documents`), which already re-keys
exactly those datasets. Together with NFC (G), plan **one** dataset
`KIND_VERSION` bump (4 → 5, `dataset.rs:34`) for v0.2. See Decision 9.
Adding `permutation_p` changes the eval output for the same inputs, so bump
`EVAL_VERSION` (3 → 4, `train.rs:26`). Old evaluations keep their saved
verdicts.

### A.6 Edge cases

- **2 documents**: auto gives 1 + 1. Say "no verdict possible; add
  documents or real queries" (exists as `DATASET_TOO_SMALL` below 2).
- **Duplicate documents** are dropped before the split
  (`dataset.rs:276-288`). Count test documents *after* that.
- **Chunks deduped across splits**: when a test chunk duplicates a training
  chunk, the test copy is removed (`dataset.rs:389-393`). A test document
  can lose all its chunks. So count test documents from the final chunk
  list, not from the split map.
- **A test document whose chunks get no queries** (the LLM failed) drops
  out of the verdict. The plan can't predict that. The post-run advice
  still covers it.
- **Real queries ≥ 30 over ≥ 10 documents** (B): the synthetic test no
  longer decides, so skip the dry-run warning, or lower it to `info`.
- **`--sample` smaller than test documents + 2**: raise it and report
  `sample_raised_to`. Don't silently drop test documents.
- **Per-language verdicts** (`by_lang`) are even smaller. Don't add
  per-language dry-run warnings: too noisy.
- **Sign-flip with zero changes**: documents whose change is exactly 0
  don't affect the count, but keep them in n. If all are 0, p = 1.

### A.7 How to test

- Unit (`dataset.rs`): auto split. (1) 11 documents give 5 test
  documents. (2) 200 documents give a split identical to
  `test_percent = 20`, and params without `min_test_documents`. (3) Adding
  a document never moves an existing test document to train when no top-up
  happened. (4) Sampling with `max_chunks` keeps every test document
  (extend `a_limit_keeps_both_splits_and_plan_counts_llm_calls`,
  `dataset.rs:1048`).
- Unit (`stats.rs`): the sign-flip test. For `[0.12, 0.05, -0.02, 0.08,
  0.10]`, p = 0.125. For n = 5 all positive, p = 0.0625 (the minimum). For
  the 11 values in 0.3, p = 0.0049 (all three from the SciPy script).
- CLI (`cli.rs`, fake trainer): a 6-document project → `train --dry-run
  --json` has `data.advice[].code == "TEST_SET_UNDERPOWERED"` with
  `evidence.predicted == true` and a dataset detail with `test_documents`.
  The same project with `--set dataset.test_percent=auto` →
  `test_documents == 3`.
- Real run: the Kaggle T4 checklist on synk's own docs with `--sample`.
  Expect the dry-run warning, then compare the verdict's `test_documents`
  with the dry run's.

| Item | Effort | Risk |
|---|---|---|
| A-1 dry-run count + warning | S (1–2 days) | Low |
| A-3 sample per test document | S (1 day) | Low (re-keys sampled datasets only) |

| A-6 refit for holdout runs | M (3–5 days after A-4) | Medium: a weaker promise, must be labelled |

## B. Real queries, end to end

### B.1 The problem, simply

Synthetic test queries come from the same LLM and prompt as the training
queries. A gain on them partly measures "the model got better at this
LLM's style of question". Your own searches don't have that problem, and
they test the model on the whole corpus, which is how you'll use it. synk
already accepts them (`synk queries import`), but nobody has a file of
past searches lying around. The missing piece is a quick way to write them.

### B.2 What synk does today

- Import format: JSONL with `query` plus `doc` and/or `text`
  (`queries.rs:1-7,69-107`). One bad line rejects the whole file
  (`queries.rs:45-59`). An empty `query` is an error
  (`queries.rs:71-78`).
- Real queries are **never trained on**. They are evaluated over **every**
  document (train and test) (`synk_sidecar.py:752-754`).
- They **decide the verdict** once there are ≥ 30 and they cover ≥ 2
  documents (`train.rs:87-88,623`). Otherwise both verdicts are reported
  under `by_kind` and the synthetic one decides (`train.rs:614-641`).
- One in four real queries (at most 5) become **style examples** for the
  LLM and are left out of evaluation (`dataset.rs:216-239`,
  `dataset.rs:414-417`).
- Import says "Next: synk train --dry-run" (`views.rs:24`).

**The weak spot:** 30 queries over 2 documents take over the verdict with
n = 2 documents, which can't produce an interval worth reading (row 2 of
the table in A.2). That replaces a possibly decisive synthetic verdict with
an almost certain "no clear change".

### B.3 Options

**B-1. `synk queries template` (cheap, must).** Write a file with one line
per selected document. You fill in the searches.

**B-2. The deciding rule: require document coverage (cheap, must).** Real
queries decide when ≥ 30 queries **and ≥ 10 documents**; otherwise report
both and let the synthetic test decide.

**B-3. Pool real and synthetic into one test (rejected).** It mixes two
different questions ("does it find held-out documents for LLM questions?"
vs "does it find my documents for my searches?") and hides disagreement.

**B-4. A query log from `synk serve` (later).** Real searches collected
while you use the model (local-rag-tooling.md #3). Out of scope here.

### B.4 Recommended design

**Command:**

```
synk queries template --out searches.jsonl [--documents 15] [--force]
```

- Picks `--documents` documents (default 15) among live documents with at
  least one chunk, skipping documents that already have real queries.
- **Spread**: deal round-robin across sources, then top-level folders, then
  detected language, each list ordered by a hash of the path. Stable: the
  same project gives the same file.
- Refuses to overwrite a non-empty `--out` without `--force`
  (`EXPORT_EXISTS`-style; reuse `INVALID_ARGS`, the same pattern as
  `train.rs:826-837`).

**File** (UTF-8, JSONL so the existing importer reads it):

```json
{"_help": "For each line, write how you would search for something you remember is in this document, WITHOUT opening it. Type it as you really would (no accents, English words, typos are all fine). Leave \"query\" empty to skip a document. Copy a line to add a second search. Then run: synk queries import searches.jsonl"}
{"template": 1, "doc": "notes/nginx.md", "title": "Nginx tuning", "lang": "vi", "query": ""}
{"template": 1, "doc": "notes/postgres-vacuum.md", "title": "Postgres maintenance", "lang": "en", "query": ""}
{"template": 1, "doc": "wiki/onboarding.docx", "title": "Onboarding", "lang": "vi", "query": ""}
```

No document text goes into the file: only path, title and language.

**Import changes** (`queries.rs`):

- Skip lines with `_help`.
- Skip lines with `"template": 1` and an empty `query`. Count them in a new
  `skipped_empty` field. Lines without `template` keep today's rule (an
  empty query is an error), so the meaning of existing files doesn't
  change.
- Report `documents` (distinct documents covered).

```json
{"v": 1, "ok": true, "data": {"added": 22, "unchanged": 0, "removed": 0, "total": 22,
  "skipped_empty": 3, "documents": 12, "next": "synk train --dry-run",
  "advice": []}}
```

**Command output** (template):

```json
{"v": 1, "ok": true, "data": {"path": "searches.jsonl", "documents": 15,
  "lines": 15, "next": null,
  "actions": [{"argv": ["synk", "queries", "import", "searches.jsonl"],
               "applicability": "manual",
               "why": "after you fill in the searches"}]}}
```

`next` is `null` on purpose. Importing an unfilled template would fail, and
AGENTS.md requires `next` to run as written *and* make sense. The import is
a manual step, so it goes in an action. Human output prints the
instructions:

```
Wrote searches.jsonl: 15 documents.

Open it in an editor. For each line, without opening the document, write
how you would search for something you know is in it. Aim for 30 searches
over at least 10 documents: copy a line to add a second search. Leave a
line empty to skip it.

Then: synk queries import searches.jsonl
```

**Why "without opening the document".** If you write while reading, you
copy its words. The search then matches the text word for word, and any
model, even a plain keyword search, finds it. The test becomes too easy and
stops measuring what tuning is for: matching *your* words to *its* words.
Lee, Chang & Toutanova found that "on datasets where the questioner already
knows the answer, a traditional IR system such as BM25 is sufficient",
while learned retrieval wins clearly where users genuinely seek the answer
([ORQA, arXiv 1906.00300](https://arxiv.org/abs/1906.00300)).

**How many, how spread.** The unit is a document (Part 0.2), so documents
count more than queries. 30 queries over 15 documents beat 60 queries over
3. Rule of thumb from the table in A.2: 10 documents see gains of ~0.10,
20–30 documents see ~0.05 (sd 0.10). One or two queries per document is
enough.

**The deciding rule (B-2).** In `decide()` (`train.rs:623`):

```
real decides  ⇔  real queries ≥ 30  AND  real test documents ≥ 10
```

(`MIN_REAL_DOCUMENTS = 10`, **[threshold unverified]**: tune it on the
benchmark.) Changing it changes verdicts for the same inputs, so bump
`EVAL_VERSION`. New verdict field `agreement`, present when both kinds
exist:

| `agreement` | Meaning |
|---|---|
| `agree` | Both kinds give the same outcome |
| `disagree` | One says `better`, the other `worse`, or one decisive and the other the opposite direction |
| `real_inconclusive` | Real queries say `no_clear_change` while synthetic is decisive |

**New advice:**

- `REAL_QUERIES_FEW_DOCUMENTS` (warning, manual): "22 real queries cover
  only 4 documents. Real searches decide the verdict once 30 or more cover
  at least 10 documents; write a few for other documents: synk queries
  template --out more-searches.jsonl". The action command is runnable
  (concrete path), `applicability: "manual"`.
- `SYNTHETIC_REAL_DISAGREE` (warning, review), when `agreement ==
  "disagree"`: "Your real searches and the LLM-written test disagree.
  Trust the real searches; the synthetic test may reward the LLM's style."

**Style pool interaction.** Imported template queries can become style
examples. Today that changes the generator's cache key and can re-ask the
LLM for every chunk (I.1). Fix I.1 before shipping the template, or the
first import after training costs hours of LLM time.

### B.5 Edge cases

- **A path renamed after the template was written**: import already fails
  that line with "no document `…`" (`queries.rs:122`). Keep the
  whole-file rejection, with the line number.
- **The same search for two documents**: allowed. Both are real queries.
  Dedup happens on import as today (`synk-store` `import_real_queries`).
- **Searches about training documents**: fine. The real verdict asks "is
  the tuned model better on my searches over my corpus?". It does not
  measure generalization to unseen documents; the synthetic test does. Say
  so in GLOSSARY ("real query").
- **Diacritic-free Vietnamese searches** (`tang timeout nginx`): welcome.
  They are what users type. whatlang can't detect their language (G.3), so
  they land in `by_lang.unknown`. That's fine.
- **Very short corpora** (< 10 documents): real queries can never decide.
  The template should say "your project has 7 documents; real searches
  can't decide the verdict but are still reported".
- **Fewer than 4 real queries**: no style examples (`dataset.rs:235`,
  `len / 4`). Unchanged.

### B.6 How to test

- Unit (`queries.rs`): `_help` lines skipped; `template` lines with an
  empty query skipped and counted; non-template lines with an empty query
  still rejected.
- Unit (`train.rs`): 30 real queries over 2 documents → `query_kind ==
  "synthetic"`, `agreement` present. 30 over 10 → `real`. Extend
  `enough_real_queries_decide_the_verdict` (`train.rs:875`).
- CLI: `synk queries template --out t.jsonl --json` on `bigger_project()`
  → `data.documents`, every line has `doc` and an empty `query`, no chunk
  text in the file. Fill 3 lines programmatically, import →
  `skipped_empty == 12`. A line in the help template (`main.rs:23-59`; the
  test at `main.rs:546` checks it).
- Real run: the owner writes 30 searches over 10+ of their own documents.
  Run once. Report the synthetic and real verdicts side by side in the
  release notes.

### B.7 Effort and risk

S (2–3 days) for the template, import changes, advice and rule change. Low
risk. The rule change is the only meaning change, and it only affects
projects with ≥ 30 real queries over 2–9 documents.

## C. The GGUF converter download

### C.1 The problem, simply

`synk export --format gguf` runs Python code it downloads from GitHub at
that moment, without asking. AGENTS.md says downloads need consent (fetch,
setup, or `--yes`), and README's network list doesn't mention this one.
Also, running freshly downloaded code with no checksum is a supply-chain
risk: if the download were tampered with, synk would run it.

### C.2 What synk does today

- The commit is pinned in the binary:
  `LLAMA_CPP_COMMIT = "711780ff…"` (`export.rs:24`), and passed to the
  trainer (`export.rs:229-236`).
- The sidecar downloads `https://codeload.github.com/ggml-org/llama.cpp/tar.gz/<commit>`
  into memory, extracts `convert_hf_to_gguf.py`, `conversion/` and
  `gguf-py/`, and caches them in `$SYNK_HOME/llama.cpp-<commit>`
  (`synk_sidecar.py:899-933`). There is no checksum, no consent item, and
  no fetch name.
- It runs the converter with `PYTHONPATH=<root>/gguf-py`
  (`synk_sidecar.py:1033-1052`). The trainer environment also installs the
  `gguf` pip package (`sidecar.rs:28-36`), but the commit's own `gguf-py`
  wins on `PYTHONPATH`.

Measured with the GitHub API at the pinned commit (committed 2026-10-15):

| Part | Files | Size |
|---|---|---|
| `convert_hf_to_gguf.py` | 1 | 13 KB |
| `conversion/` | ~100 | 1.13 MB |
| `gguf-py/` | 27 | 0.81 MB |
| **Needed in all** | ~128 | **~1.95 MB** |
| Whole repository (what the tarball holds) | — | 178 MB uncompressed |

So today synk downloads a tarball of the whole repository (compressed size
**[unverified]**, tens of MB) to use about 2 MB.

### C.3 Options

**C-1. A fetch name: `gguf-converter@711780f`.** `synk fetch
gguf-converter@711780f` downloads and verifies it. `synk export --format
gguf` without it fails with `CONSENT_REQUIRED` and
`details.fetch: ["gguf-converter@711780f"]`. Export also needs `--yes`
and a `--dry-run`.

- Pro: fits ADR 0002 word for word. The binary stays small.
- Con: export gains a consent flow it doesn't have today (new flags,
  preview, tests). The download is still the whole tarball, unless synk
  fetches ~128 files one by one. A checksum of the **tarball** is fragile:
  GitHub only promised "byte-for-byte stable" archives "for no less than a
  year" from 2023-02-21, with six months' notice before changes
  ([GitHub blog](https://github.blog/2023-02-21-update-on-the-future-stability-of-source-code-archives-and-hashes/)),
  and its changelog says auto-generated archives aren't guaranteed stable
  ([changelog](https://github.blog/changelog/2023-01-30-git-archive-checksums-may-change/)).
  So check a SHA-256 **per extracted file** against a manifest built at
  release time, not the tarball's hash.

**C-2. Vendor the converter: ship the ~2 MB inside synk.** At release
time, a script copies the three paths at `LLAMA_CPP_COMMIT` into
`crates/synk-pipeline/vendor/llama.cpp/`, with llama.cpp's `LICENSE`.
`include_bytes!` a zip of it (the `zip` crate is already a dependency of
`synk-connectors`). On first GGUF export, unpack it into
`$SYNK_HOME/gguf-converter-<commit12>/` (as the sidecar script is written
today, `sidecar.rs:292-299`).

- Pro: no download at all, so no consent is needed and offline export
  works. The code that runs is the code that was reviewed and released.
  **The update burden is the same as today**: the commit is already
  compiled in (`export.rs:24`), so any converter update already needs a
  release.
- Con: +~2 MB in the repo per bump (~0.5 MB compressed in the binary
  **[estimate]**). It must keep the MIT notice: llama.cpp is "MIT License,
  Copyright (c) 2023-2026 The ggml authors"
  ([LICENSE](https://github.com/ggml-org/llama.cpp/blob/master/LICENSE)).
  The vendored folder must be excluded from `cargo fmt`/clippy (it's
  Python, so no issue) and from line-count noise.

**C-3. Only the `gguf` pip package.** The PyPI `gguf` package (0.19.0,
2026-05-06) is "a Python package for writing binary files in the GGUF
format". It does not include `convert_hf_to_gguf.py`; its own TODO says
the project still needs to "Include conversion scripts as command line
entry points" ([PyPI](https://pypi.org/project/gguf/)). synk would have to
write its own BERT/XLM-R → GGUF mapping, including the tokenizer metadata.
That is a correctness risk every time llama.cpp changes its expectations.
Rejected.

**C-4. Drop GGUF.** It's the path to Ollama, and so to Open WebUI and
AnythingLLM (H). Users would lose the simplest local integration.
Rejected.

### C.4 Recommended design: C-2 (vendor), consistent with ADR 0002

ADR 0002's rule is "never download without consent". Vendoring removes the
download, which satisfies the rule more strongly than a fetch name. Record
this as a new ADR ("Vendor llama.cpp's GGUF converter"), because it
changes what the binary contains.

- `crates/synk-pipeline/vendor/llama.cpp/{LICENSE, convert_hf_to_gguf.py,
  conversion/, gguf-py/, VENDORED.toml}`. `VENDORED.toml` holds the commit,
  the date, and a SHA-256 per file.
- `scripts/vendor-llama-cpp.sh <commit>` regenerates it (uses
  `gh api`/`git archive`; dev-only).
- Build: a `build.rs` zips the folder into `OUT_DIR`, and
  `include_bytes!(concat!(env!("OUT_DIR"), "/llama-cpp.zip"))` embeds it.
  Or simpler: commit the zip and embed it. **Decision 3.**
- Request to sidecar: replace `"llama_cpp_commit"` + `"cache_dir"` with
  `"converter_dir"` (added field). The sidecar uses it when present and
  **never downloads**. Delete `llama_cpp()`'s download branch.
  Changing the request bumps nothing on the trainer side: export has no
  cached artifact.
- `synk export ... --json` adds `"converter": {"name": "llama.cpp",
  "commit": "711780f", "license": "MIT"}` (add-only).
- README Privacy section: unchanged ("export talks to your local Ollama").
  The download that was missing from that list no longer exists.
- Third-party notice: list llama.cpp under "Included software" in README,
  and ship its LICENSE with release archives (`dist-workspace.toml`
  include, **[check the dist option name]**).

If the owner prefers C-1, use a **per-file manifest** for verification,
keep the fetch flow in `fetch.rs` (`Work::Converter`), and give `export`
`--dry-run`/`--yes`. Effort M instead of S.

### C.5 Edge cases

- **The trainer's `gguf` pip package vs. the vendored `gguf-py`**: keep
  `PYTHONPATH` pointing at the vendored copy, so the converter always uses
  the `gguf-py` from its own commit.
- **The converter needs `torch`, `numpy`, `transformers`, `sentencepiece`**:
  already in the environment (`sidecar.rs:23-36`).
- **A user-supplied `trainer.python`** without `sentencepiece`: same as
  today. The conversion fails with `EXPORT_UNSUPPORTED` and the converter's
  last lines (`synk_sidecar.py:1049-1051`).
- **Two synk versions on one machine**: unpack into a folder named after
  the commit, so they don't clash.
- **New model families (granite r2, ModernBERT)** need a newer commit
  **[unverified whether the pinned commit supports it]**. That is a synk
  release, as today.

### C.6 How to test

- Unit: the embedded zip unpacks, every file's SHA-256 matches
  `VENDORED.toml`, and `LICENSE` is present.
- Unit: `synk_sidecar.py` has no `urllib` import left
  (`include_str!` the script and assert in a Rust test; cheap and stops
  regressions).
- e2e (ignored test, `cli.rs:1175`): it already exports GGUF. Run it with
  the network blocked for the export step (e.g. `HTTPS_PROXY=http://127.0.0.1:9`)
  to prove no download happens.

### C.7 Effort and risk

S (2–3 days including the ADR). Low risk: the same files, now local.

## D. Ctrl-C and killed processes

### D.1 The problem, simply

You press Ctrl-C during training. Today:

1. synk dies at once. Rust's default action for SIGINT/Ctrl-C ends the
   process **without running destructors**, so `Op::drop` (which marks the
   record failed and removes the lock, `ops.rs:828-843`) never runs.
2. The Python trainer **also** receives Ctrl-C. Both are in the
   terminal's foreground process group on Linux/macOS, and on Windows
   "these signals are passed to all console processes that are attached to
   the console" ([Microsoft](https://learn.microsoft.com/en-us/windows/console/ctrl-c-and-ctrl-break-signals)).
   Python turns it into `KeyboardInterrupt`, which is a `BaseException`.
   The sidecar's `except Exception` doesn't catch it
   (`synk_sidecar.py:1079-1087`), so the trainer prints a traceback and
   exits **without** the "save a checkpoint, then stop" path
   (`synk_sidecar.py:601-608`). The run resumes from the last periodic
   checkpoint (every ~10% of steps, `synk_sidecar.py:641-643`), not from
   where you stopped.
3. `.synk/lock` still names the run, and its record still says `running`.
   For up to 120 s (`ops.rs:36`), `synk train` fails with `JOB_RUNNING`.

A second, quieter problem: liveness is "the heartbeat is younger than
120 s" (`ops.rs:199-210`). If a laptop sleeps for 3 minutes mid-run, the
record reads as `interrupted` after waking, and a second `synk train` can
start **while the first is still alive**.

### D.2 What synk does today

- No signal handler anywhere in the workspace (no `ctrlc`/`signal-hook`
  dependency, workspace `Cargo.toml`).
- `synk cancel` creates `.synk/ops/<op>/cancel` (`ops.rs:436-444`). It is
  checked between steps (`exec.rs:110`), per chunk during query generation
  (`exec.rs:180`), and by the trainer at every progress report and training
  step (`synk_sidecar.py:40-54,601-608`). Training saves a checkpoint, then
  fails with `CANCELLED` (`synk_sidecar.py:682-683`). The record becomes
  `cancelled` (`ops.rs:806-810`). This path works and is tested
  (`cli.rs:707-797`).
- The child is spawned with stdout piped, stderr to a log and **stdin
  inherited** (`sidecar.rs:198-210`). It dies with its parent only
  indirectly: its next write to the closed stdout pipe fails.
- Exit codes: 0 success, 2 usage, 1 everything else (`output.rs:52-71`).

### D.3 Options

**Catching Ctrl-C in Rust:**

- **`ctrlc` 3.5.2**: on Unix it handles SIGINT; on Windows `CTRL_C_EVENT`
  or `CTRL_BREAK_EVENT`. The `termination` feature adds SIGTERM and
  SIGHUP. The handler runs on "a new dedicated signal handling thread".
  Only one handler is allowed per program
  ([docs.rs](https://docs.rs/ctrlc/latest/ctrlc/)). Small, widely used.
  Recommended.
- `signal-hook` (Unix only) + raw `SetConsoleCtrlHandler` (Windows): more
  control, more code. Not needed.

**Keeping the terminal's Ctrl-C away from the child** (so only synk
decides how to stop it):

- Unix: `std::os::unix::process::CommandExt::process_group(0)` puts the
  child in its own process group, so the terminal's SIGINT (sent to the
  foreground group) doesn't reach it.
- Windows: `CREATE_NEW_PROCESS_GROUP`: "CTRL+C signals will be disabled
  for all processes within the new process group"
  ([process creation flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)).
  Set it with `std::os::windows::process::CommandExt::creation_flags`.

**Making the child die with the parent** (also on SIGKILL, a crash, or a
closed terminal):

- **A lifeline pipe (portable, recommended).** Spawn the child with
  `stdin` piped and keep the write end open. A thread in the sidecar
  blocks on `sys.stdin.read()`. When it returns (EOF: synk is gone), it
  sets the stop flag. Training then stops at the next step with a
  checkpoint. If the process hasn't exited 60 s later, `os._exit(3)`. Works
  the same on every OS. The only caveat: a child stuck inside one long call
  (a CUDA kernel, a tokenizer on a huge batch) notices at the next step.
- **Windows job object** with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`:
  "Causes all processes associated with the job to terminate when the last
  handle to the job is closed"
  ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information)).
  When synk dies, Windows closes its handles, so the child is killed. A
  hard kill, a good backstop.
- **Linux `prctl(PR_SET_PDEATHSIG)`**: Linux only, set in the child (Python
  can't easily). Skip; the lifeline covers it.
- **The `process-wrap` crate 10.0.1** ("a more flexible and composable
  successor to the `command-group` crate"): `JobObject` (Windows),
  `ProcessGroup`/`ProcessSession` (Unix), behind features, with a `std`
  frontend ([docs.rs](https://docs.rs/process-wrap/latest/process_wrap/)).
  One dependency for both OSes, or ~50 lines of `windows-sys` for the job
  object alone. **Decision 7.**

**Knowing the run's process is dead, at once:** see F. An OS file lock
held for the operation's lifetime is released by the OS when the process
dies. Then "running" means "someone holds the lock", not "the heartbeat is
recent".

### D.4 Recommended design

**One handler, installed at startup** (`main.rs:395`), with the `termination`
feature (so an agent's shell that sends SIGTERM on timeout gets the same
graceful path):

```
state: static INTERRUPTS: AtomicUsize
       static CURRENT: Mutex<Option<Interruptible>>   // set by Ops::begin, cleared by finish
       Interruptible { cancel_file, child_killer, record_writer }

on signal:
  n = INTERRUPTS.fetch_add(1) + 1
  if no CURRENT (e.g. a dry run, status):  exit 130 at once (nothing to protect)
  n == 1: create cancel_file
          stderr: "Stopping at the next safe point (training saves a checkpoint first). Press Ctrl-C again to stop now."
          with --progress jsonl: {"v":1,"event":"interrupt","count":1,"next":"wait"}
  n >= 2: kill the child (job object terminate / kill the process group)
          record: state cancelled, done, reason "stopped at once by a second Ctrl-C; continues from the last checkpoint"
          release the lock
          stdout: the one CANCELLED error object (--json), exit 130
```

The first press uses the **existing** cancel path. Everything downstream
(the trainer's checkpoint, `CANCELLED`, the record, the `next` hint
`synk train run:3`) already works and is tested. The main thread then
returns normally, so stdout still gets exactly one result object.

**Spawning the trainer** (`sidecar.rs:198`):

- Unix: `.process_group(0)`. Windows: `.creation_flags(CREATE_NEW_PROCESS_GROUP)`
  plus assigning the child to a kill-on-close job object.
- `.stdin(Stdio::piped())`, keeping the `ChildStdin` alive until the child
  exits.
- Request field `"lifeline": "stdin"` (added field, protocol v2). The
  sidecar starts the watcher thread only when it's set, so running the
  script by hand still works.

**Sidecar** (`synk_sidecar.py`):

```python
import threading, signal

STOP = threading.Event()

def stop_requested():
    return STOP.is_set() or (bool(STOP_FILE) and os.path.exists(STOP_FILE))

def watch_lifeline():
    sys.stdin.read()        # returns at EOF: synk is gone
    STOP.set()
    time.sleep(60)
    os._exit(3)             # didn't reach a safe point in time

# in main(), when req.get("lifeline") == "stdin":
threading.Thread(target=watch_lifeline, daemon=True).start()
# and treat a stray SIGINT (e.g. someone ran the script by hand) as a stop request:
signal.signal(signal.SIGINT, lambda *_: STOP.set())
```

Also catch `KeyboardInterrupt` in `main()` and report it as `CANCELLED`,
for runs started by hand.

**Record and output** after the first Ctrl-C (unchanged shape, new
`reason` text):

```json
{"v": 1, "ok": false, "error": {"code": "CANCELLED", "class": "failed", "retryable": true,
  "message": "run:3-e5-small was cancelled (Ctrl-C); training stopped after a checkpoint",
  "next": "synk train run:3",
  "details": {"id": "run:3-e5-small", "how": "ctrl_c"}}}
```

`details.how` is new: `"ctrl_c"`, `"ctrl_c_twice"`, `"cancel"` (synk
cancel), `"terminated"` (SIGTERM). Exit code **130** for an interrupt (the
shell convention for "ended by SIGINT"). **Decision 5.** README's exit-code
line becomes "0 when `ok`; 2 for usage errors; 130 when interrupted;
otherwise 1".

**Heartbeat.** Keep writing it (it shows "last seen" and feeds `progress`),
but stop using it to decide liveness. F's OS lock does that. `STALE_AFTER`
stays only for records written by synk 0.1 (no `liveness` field), so a
mixed-version project still works.

**What a killed run looks like** (SIGKILL, a closed laptop lid that never
comes back, a crash):

```
$ synk wait --json        # immediately after the kill
{"v":1,"ok":true,"data":{"id":"run:3-e5-small","state":"interrupted","done":true,
 "reason":"the process that ran it (pid 4120) stopped; continue with: synk train run:3",
 "next":"synk train run:3", ...}}
```

### D.5 Edge cases

- **Ctrl-C during `synk fetch`** (Hugging Face downloads happen in the
  trainer's `fetch` task, `synk_sidecar.py:215`): the first press stops at
  the next progress report. HF downloads resume, so a second press is
  harmless.
- **Ctrl-C during an Ollama pull**: the pull is an HTTP stream in Rust.
  Check `cancel_requested()` between stream chunks **[verify in
  `generator.rs`/`fetch.rs`; I did not trace the pull loop]**. Ollama keeps
  partial downloads.
- **Ctrl-C during `synk setup`**: uv runs as a child in synk's process
  group, so it gets Ctrl-C and stops. An interrupted install is rebuilt
  next time (`sidecar.rs:399-405`). Don't move uv to its own group; a fast
  stop is right there.
- **Ctrl-C during query generation**: one LLM call can take minutes on a
  CPU. The cancel is checked per chunk (`exec.rs:180`); the generated
  queries so far are cached. The second press is the escape hatch.
- **Ctrl-C in a dry run or a read-only command**: no operation is running,
  so exit at once (130).
- **Closing the console window on Windows** sends `CTRL_CLOSE_EVENT`.
  `ctrlc` documents only CTRL_C and CTRL_BREAK on Windows, so this
  probably isn't caught **[unverified with the `termination` feature]**.
  The job object and the OS lock still clean up.
- **The handler thread and stdout**: the handler must not print the result
  object on the first press (the main thread does). On the second press it
  prints and exits. Guard stdout with a `Mutex` so the two can't
  interleave.
- **Nested synk processes** (an agent runs `synk wait` while `train` runs):
  each has its own handler. `wait` has no `CURRENT`, so Ctrl-C there exits
  at once and never cancels the run. That's the right behaviour; `synk
  cancel` is the way to cancel from another shell.

### D.6 How to test

1. **Unit (`ops.rs`)**: an `interrupt(n)` function, separate from the
   signal plumbing. `n = 1` creates the cancel file. `n = 2` marks the
   record cancelled with `how = "ctrl_c_twice"` and frees the lock.
2. **CLI, every OS: hard kill.** Spawn `synk --json train` with
   `SYNK_FAKE_TRAINER_SLOW=20000`, wait until it runs (as in
   `cli.rs:722-738`), `child.kill()` (TerminateProcess / SIGKILL). Then
   `synk wait --timeout 0s --json` must show `interrupted` **within 1 s**,
   and `synk train` must continue it (`attempt == 2`), not fail with
   `JOB_RUNNING`. This proves the OS-lock liveness (F).
3. **CLI, Unix: real SIGINT.** `kill -INT <pid>` via `Command::new("kill")`
   (no new dev-dependency). Expect exactly one stdout object with
   `CANCELLED`, `details.how == "ctrl_c"`, exit code 130, state
   `cancelled`. Two SIGINTs 100 ms apart with a 60 s slow step → exits in
   under 2 s.
4. **CLI, Windows: the same logic, via a test hook.** Sending a console
   Ctrl-C from a test is fragile (`GenerateConsoleCtrlEvent` needs a shared
   console). Add a debug-build-only env var
   `SYNK_TEST_INTERRUPT_AFTER_MS` that calls the same `interrupt()` from a
   timer. That runs on all OSes in CI. Plus one manual check in Windows
   Terminal per release.
5. **A child-process fake.** The fake trainer runs in-process
   (`fake_trainer.rs`), so it can't test process groups or the lifeline.
   Add `SYNK_FAKE_TRAINER=process`: synk re-runs its own binary with a
   hidden `__fake-sidecar` subcommand that speaks the protocol, reads the
   lifeline, and sleeps. Test: kill synk → the fake child exits within 5 s
   (check with `sysinfo` or `ps`/`tasklist` in the test).
6. **e2e (ignored, real Python)**: kill synk during training, assert the
   Python process is gone within 70 s (lifeline + 60 s grace), and that
   `synk train` resumes from a checkpoint (`resuming from checkpoint-N` in
   the log).

|---|---|---|

## E. Disk space

### E.1 The problem, simply

A first run on a laptop downloads ~1–3.5 GB of trainer, ~5 GB of LLM and
~0.5–2 GB of model, then writes checkpoints that are several times the
model's size. If the disk fills at minute 40 of training, the user sees
`SIDECAR_FAILED` with a Python traceback, and possibly a half-written
checkpoint. Nothing checks first.

### E.2 What synk does today

- No free-space check anywhere. `ErrorCode::InsufficientDisk` exists
  (`error.rs:44,118`), class `resource` (`error.rs:206`), but **nothing
  raises it**, and README's error table doesn't list it
  (`README.md:332-355`).
- Download sizes are known in the preview: trainer 1.0 / 3.5 GB (rough,
  `graph.rs:34-35`), Hugging Face repos from the Hub API
  (`graph.rs:582-600`), Ollama models from the registry
  (`graph.rs:812-816`). Totals: `totals.download_bytes`
  (`graph.rs:1050`).
- Training writes checkpoints with optimizer state, keeps one
  (`save_total_limit=1`, `synk_sidecar.py:641-643`), keeps a `best/` copy
  when there is a dev split (`synk_sidecar.py:614-627`), and removes them
  at the end (`synk_sidecar.py:696-698`). An interrupted run keeps them in
  `<key>.tmp/` until resumed (`train.rs:309-317`). If its settings changed,
  it's never resumed, and **the space is never freed**.
- The sidecar maps out-of-memory to `OUT_OF_MEMORY`
  (`synk_sidecar.py:673-681`) but a full disk becomes `SIDECAR_FAILED`
  (`sidecar.rs:244-256`).

### E.3 What needs space, and where

| What | Where | Size | Source |
|---|---|---|---|
| Trainer env (CPU) | `$SYNK_HOME/envs` + uv cache | 1.0 GB download; more unpacked **[unverified; measure with `du`]** | `graph.rs:34` |
| Trainer env (CUDA) | same | 3.5 GB download; unpacked likely 2× **[unverified]** | `graph.rs:35` |

**Training peak, worked out** (**[estimate; measure on a real run]**):

AdamW keeps two extra numbers per trainable weight (its running mean and

best/ (merged)     ≈ 2.3 GB
model + .tmp       ≈ 2.3–4.6 GB
peak in .synk      ≈ 5–7 GB;  after the run: ≈ 2.3 GB

### E.4 Querying free space in Rust

- **`fs4` 1.1.0**: `pub fn available_space<P: AsRef<Path>>(path: P) ->
  Result<u64>` "Returns the available space in bytes to non-privileged
  users in the file system containing the provided path". Unix and Windows
  ([docs.rs](https://docs.rs/fs4/latest/fs4/fn.available_space.html)).
  Small; exactly what's needed. **Recommended.**
- `sysinfo` 0.39.6: `Disk::available_space()`, but you find the disk for a
  path yourself by matching mount points
  ([docs.rs](https://docs.rs/sysinfo/latest/sysinfo/struct.Disk.html)).
  Heavier; only worth it if synk also wants it for process checks.
- The path must exist. Walk up to the nearest existing ancestor
  (`.synk/artifacts` may not exist on a fresh project).
- **Same volume?** Group needs by volume so two items on one disk add up.
  Unix: `MetadataExt::dev()` of the nearest existing ancestor. Windows: the
  path prefix (drive or UNC share) after `dunce::canonicalize` (already a
  dependency).

### E.5 Options for where to check

**E-1. In the preview, as a blocker (recommended).** `graph::make` sums the
bytes per volume for the steps that will `run`, compares with free space,
and adds an `INSUFFICIENT_DISK` blocker. Cheap (one syscall per volume). It
shows in `--dry-run` before anything is spent.

**E-2. Right before each step (recommended, as well).** Space changes
between the dry run and minute 40. Re-check before `Step::Train` in
`exec.rs` (and before each fetch item in `fetch.rs`).

**E-3. Only map the runtime error.** Necessary but too late on its own.

Do all three.

- **The HF cache on Windows without Developer Mode** stores copies instead

- **Re-runs**: if the train step is `cached`, it needs 0 bytes. Only `run`

- **Resuming an interrupted run**: its `.tmp` already holds one

S–M (3–5 days). Low risk, apart from false blocks from bad estimates (hence

## F. The project lock race

### F.1 The problem, simply

Two `synk train` commands start at the same moment (an agent retries while
the first is still starting). Both read `.synk/lock`, both see "nothing
running", both write it, and both run. They then share datasets, the query
cache and run numbers.

### F.2 What synk does today

- `start()` calls `check_free()` (reads the lock, `ops.rs:461-475`), then
  checks the name, prunes, takes a number (`next_number`, `ops.rs:420-434`:
  read `seq.json`, write it back), and only then `begin()` writes the lock
  with plain `fs::write` (`ops.rs:562-567`). Everything in between is a
  window for a second process.
- `dataset_number(key, true)` is called **before** `start()` for dataset
  builds (`work.rs:680-683`), outside any lock, so two builds can collide
  on `datasets.json` (`ops.rs:398-411`).
- Liveness is the heartbeat age (`ops.rs:199-210`; see D.1 for the sleep
  problem).

### F.3 Options

**F-1. `create_new` on the lock file.** `OpenOptions::new().write(true)
.create_new(true)` is atomic: "if the call succeeds, the file returned is
guaranteed to be new"
([std](https://doc.rust-lang.org/std/fs/struct.OpenOptions.html)). It fixes
the race. A dead process still leaves the file behind, though, so you
still need the heartbeat or a pid check to recover. And pid checks are
fragile: pids get reused.

**F-2. An OS file lock held for the operation's lifetime (recommended).**
`File::try_lock()` (stable since Rust 1.89, `flock(LOCK_EX|LOCK_NB)` on
Unix, `LockFileEx` on Windows). "The lock will be released when this file
(along with any other file descriptors/handles duplicated or inherited from
it) is closed" ([std](https://doc.rust-lang.org/std/fs/struct.File.html)).
The OS closes every handle of a dead process, so the lock frees itself on
a crash, a SIGKILL or Ctrl-C. synk's MSRV is 1.98 (workspace
`Cargo.toml`), so no new crate is needed. It fixes the race *and*
liveness.

**F-3. A lock directory (`mkdir` is atomic).** Same staleness problem as
F-1. No advantage.

### F.4 Recommended design (F-2)

Two files, because on Windows `LockFileEx` blocks *other processes from
reading* the locked bytes, and readers need the ID:

- `.synk/lock.held`: empty, held with `try_lock()` by the running
  operation for its whole life (stored in `Op`).
- `.synk/lock`: the running operation's ID, as today, so `running()` and
  old readers keep working.

**Start:**

```
open .synk/lock.held (create, write) → try_lock()
  WouldBlock → retry for up to 1 s (a reader may hold it briefly, see below)
             → still blocked: read .synk/lock → JOB_RUNNING (as today)
  Ok        → we own the project:
              settle a stale `running` record (state interrupted, reason names its pid)
              take the number (seq.json / datasets.json), write op.json,
              write .synk/lock (write tmp + rename), keep the File in `Op`
```

Move `next_number` and `dataset_number(assign = true)` **after** taking
the lock (`work.rs:680-683` → inside `start`). Then numbering is
race-free too.

**Liveness check** (`running()`, `settle()`):

```
read .synk/lock → id → read op.json
if record.state == running:
   try_lock .synk/lock.held from this process:
      Ok         → nobody holds it: the process died → unlock at once,
                   report interrupted ("the process that ran it (pid N) stopped")
      WouldBlock → it is running
```

The reader holds the lock for microseconds; the 1 s retry in `start`
covers that window.

**Compatibility:** records gain `"liveness": "os_lock"` (add-only). Records
without it (written by 0.1) keep the heartbeat rule (`STALE_AFTER`). On a
filesystem where locking fails with "unsupported" (some network shares
**[unverified which]**), fall back to `create_new` + heartbeat and set
`"liveness": "heartbeat"`.

**Finish/Drop:** drop the `File` (unlocks), remove `.synk/lock`. If the
process dies, the OS unlocks and `.synk/lock` is left behind, which is
harmless: readers check the OS lock.

### F.5 Edge cases

- **Two handles in one process**: `flock` locks belong to the open file
  description, so two `open()`s in one process conflict, as needed by
  tests that start two ops from two threads. `LockFileEx` is per handle.
  The docs say re-locking through *the same* handle is "unspecified"; never
  do that.
- **Sleep/resume**: the lock stays held across sleep, so a sleeping run is
  correctly `running`. The heartbeat age then only feeds "last seen 4 min
  ago" in `synk wait`.
- **A forked child holding the lock**: the trainer is spawned, not forked
  with inherited handles. Rust's `Command` doesn't leak file descriptors
  (`O_CLOEXEC` by default on Unix) **[verify on Windows: handles aren't
  inherited unless marked inheritable; Rust creates them non-inheritable]**.
  Otherwise a live Python child would keep the lock after synk dies, which
  is acceptable anyway (the run's work is still happening) but would
  delay recovery until the lifeline stops it.
- **Lock file on a read-only project**: then nothing can run anyway; the
  error is `IO` as today.

### F.6 How to test

- Unit (`ops.rs`): start from two threads at once (a `Barrier` before
  `start`) → exactly one `Ok`, one `JOB_RUNNING`. Repeat 50 times.
- Unit: start an op, then (in the same test) open a *second* handle and
  `try_lock` → `WouldBlock`. Drop the `Op` without `finish` → a new
  `start` succeeds and the old record reads `interrupted`, not `failed`
  (or `failed` from Drop; see `ops.rs:828-843`, which stays for panics).
- CLI: two `synk --json train` processes spawned back to back with the
  slow fake trainer → exactly one prints `JOB_RUNNING`, and the run numbers
  in `.synk/ops/` are unique.
- CLI: the hard-kill test from D.6 (2).

### F.7 Effort and risk

S (2 days). Low risk. The main thing to get right is the ordering (lock,
then number), and the Windows read restriction (hence two files).

## G. Vietnamese text hygiene and the PDF spike

### G.1 The problem, simply

Vietnamese letters can be stored in two ways. "ế" can be **one** code point
(U+1EBF, "NFC") or **three** (e + circumflex + acute, "NFD"). They look the
same on screen but are different bytes. Files from macOS, some Word
versions, or copy-paste can carry NFD. Consequences in synk:

- **Language detection fails.** Measured: whatlang detects NFD "Tiếng
  Việt" as **Latvian** (confidence 0.09), NFC as Vietnamese.
- **Matching fails.** A real query typed in NFC doesn't `contains()` an
  NFD passage (`queries.rs:22-27,85-87`), and the duplicate checks
  (`dataset.rs:370-399`) treat NFC and NFD copies as different.
- **Tokenization** probably doesn't care. XLM-R-family tokenizers normalize
  NFKC-style internally **[unverified per model]**.

Separately, notes that mix Vietnamese and English are detected badly.
Measured with whatlang 0.18 (synk's version and its 0.5 confidence floor,
`lang.rs:110-114`):

| Text | whatlang | Confidence | synk today |
|---|---|---|---|
| Tăng keepalive_timeout lên 75s trong nginx.conf rồi reload service | vi | 0.59 | vi |
| Cấu hình Redis cluster: set maxmemory-policy allkeys-lru, bật appendonly yes | Latin | 0.05 | none |
| Kubernetes deployment rollout restart khi config map thay đổi | Catalan | 0.06 | none |
| API gateway rate limit 100 req/s per user, dùng token bucket | **French** | **0.84** | **fr** (wrong) |
| tang timeout nginx | Tagalog | 0.29 | none |
| deploy lên k8s bằng helm chart, check pod logs nếu CrashLoopBackOff | vi | 1.0 | vi |
| docker compose up -d, sau đó vào http://localhost:8080 để kiểm tra | vi | 1.0 | vi |

A wrong `fr` matters: the prompt then asks the LLM for queries "in the
same language as the passage (French)" (`generator.rs:328-343`), and the
query is counted under `fr` in `by_lang`. Chunks are longer than these
lines, so real chunks are detected better **[measure on the owner's
notes]**.

### G.2 What synk does today

- `readers::normalize` trims line ends and collapses blank lines, with no
  Unicode normalization (`readers.rs:118-136`).
- A file whose bytes are unchanged is **never re-read**: the hash check
  skips it (`fs.rs:116-133`). So a reader change doesn't reach existing
  documents until each file is edited.
- The document hash is of the **file bytes** (`fs.rs:129`). The dataset key
  uses those hashes (`dataset.rs:316-325`), not the extracted text, while
  chunk IDs and the query cache use the **text** (`dataset.rs:296,300`).
- PDF: `pdf-extract` 0.12, panics caught (`readers.rs:270-288`). The
  garbled-text check counts only U+FFFD and control characters
  (`readers.rs:290-305`), so TCVN3/VNI mojibake (Latin-looking letters)
  passes as good text.

### G.3 Options and recommended design

**G-1. NFC at read time (must).** Apply `nfc()` from `unicode-normalization`
(0.1.25 is already in `Cargo.lock`, pulled in by another dependency, so it
adds no new code to the build) to every reader's output, inside
`readers::normalize`. Also apply it to imported real queries and passages
(`queries.rs`), and to LLM-generated queries before caching.

The re-read problem, and its fix: **a reader version.**

- `synk-connectors` exports `READER_VERSION: u32` (1 → 2 with NFC).
- The store gets a new migration (appended, never edited): `CREATE TABLE
  meta (key TEXT PRIMARY KEY, value TEXT NOT NULL)`, holding
  `reader_version`.
- When the stored version is lower, the next sync re-reads every file (it
  skips the size/mtime and hash shortcuts), but **upserts only documents
  whose text changed**, and reports them as `reread: N` (a new field in the
  sync totals), not as "changed". The `content_hash` (file bytes) stays the
  same.
- Since the dataset key comes from file hashes, add `"reader":
  READER_VERSION` to the dataset params. That re-keys every dataset once
  (Decision 9). Chunks whose text didn't change keep their chunk hash, so
  **only NFD chunks are re-sent to the LLM**. For most projects that is
  none.

**G-2. Detect Vietnamese by its letters first (should).** Before
whatlang:

```
letters  = alphabetic chars (after NFC)
vi_only  = ă đ ơ ư (any case) + U+1EA0..U+1EF9 (Latin Extended Additional, the Vietnamese block)
if vi_only / letters ≥ 0.02 → vi
else → whatlang, with an allowlist when generator.languages is set, confidence ≥ 0.5
```

Measured on the lines above (share of Vietnamese-only letters): the Redis
line 3.2% → vi, the Kubernetes line 3.8% → vi, the nginx line 3.7% → vi,
French 0% → falls through. The "token bucket" line has no Vietnamese-only
letter ("dùng" uses ù, which French also has), so it still goes to
whatlang. With an allowlist of `[vi, en]` whatlang says en at 0.45, below
the floor → none. Don't use the allowlist alone: with `[vi, en]`,
whatlang called the Redis line English at 1.0 and "how do we vacuum
postgres" Vietnamese at 0.32 (measured).

Changing detection changes chunk `lang`, and so the prompt, so bump
`PROMPT_VERSION` **or** include a detector version in the chunk hash
input. Simplest: include `lang` in the chunk `hash` (it is "everything the
prompt sees", `dataset.rs:299-300`). Then only chunks whose language
changed are re-asked.

**G-3. Legacy encodings, TCVN3 (ABC) and VNI (later, after samples).**
Older Vietnamese documents use 8-bit fonts. Their extracted text looks like
Latin-1 accented letters ("Céng hoµ x· héi chñ nghÜa ViÖt Nam" for "Cộng
hoà xã hội chủ nghĩa Việt Nam" **[example from memory; unverified]**). How
common they still are in personal notes is **[unverified]**. Recommended:
collect 3–5 real examples in the PDF spike. If any turn up, add a skip
reason `legacy_vietnamese_encoding` when (a) Vietnamese-only letters are
< 0.5% **and** (b) characters from the set typical of TCVN3 output (µ ¸ ¶ ·
¹ ¨ » ¾ ¼ ½ Æ © Ç Ê È É Ë ª Ì Ð Î Ï Ñ « Ò Õ Ó Ô Ö ¬ × Ý Ø Ü Þ ®) are >
3% of letters **[thresholds unverified]**. Skipping beats silently
training on mojibake. Converting is possible (fixed tables) but not worth
it before evidence.

**G-4. The diacritic-free eval slice (later).** People often type
Vietnamese without tone marks **[unverified how often]**. Measure before
training on it: for each Vietnamese test query, add a stripped copy (NFD,
drop combining marks, đ → d), mark it `kind: "no_diacritics"` with
`of: <original id>`, and report `verdict.by_slice.no_diacritics`. It must
not enter the main verdict: `decide()` partitions by `kind == "real"` today
(`train.rs:615-616`), so filter it out explicitly. Dataset `KIND_VERSION`
and `EVAL_VERSION` bumps. S effort; v0.3.

### G.4 The PDF spike: a checklist with your own files

Goal: decide whether `pdf-extract` is good enough for Vietnamese PDFs, with
evidence. 2–3 hours.

1. **Collect 10–20 PDFs** in a folder outside any synk project: your own
   (wiki exports, scanned contracts, slides saved as PDF), plus a few
   public ones (government legal documents are public and shareable
   **[pick a source; licensing of each file to check]**). Aim for a mix:
   Word-exported, LaTeX, scanned, with tables, and at least one old
   document likely to use TCVN3/VNI fonts.
2. **Extract with synk:**
   ```sh
   mkdir spike && cd spike && synk init && synk source add ../pdfs && synk source sync --json > sync.json
   ```
   `sync.json` lists skipped files and reasons (`no_text_layer`,
   `garbled_text`, `unreadable`).
3. **Dump the text** synk stored:
   ```sh
   sqlite3 .synk/synk.db "SELECT id, length(text), substr(text, 1, 400) FROM documents WHERE deleted = 0"
   ```
   (columns from `synk-store` migration 1, `lib.rs:20-31`).
4. **Extract the same files with a reference tool**, e.g. Poppler's
   `pdftotext -layout file.pdf -` (manual, for comparison only), and with
   `pypdfium2` in the trainer env **[an option to evaluate; adds a
   dependency if adopted]**.
5. **Score each file by hand** (a spreadsheet, 1 row per file): text
   present (y/n); Vietnamese letters intact (NFC, no `?`/boxes); reading
   order right (columns, headers/footers not mixed into sentences); tables
   readable; mojibake (TCVN3/VNI) present.
6. **Check NFC**: count files where `text != nfc(text)` (Python:
   `unicodedata.is_normalized("NFC", t)`).
7. **Check detection**: run the G-2 rule and whatlang on each document's
   first 2,000 characters; note mismatches.
8. **Decide**: if pdf-extract is right on ≥ 80% of files and the failures
   are skips (not garbage), keep it. If it produces garbage that passes the
   quality check, tighten `pdf_quality` first. Consider a second reader
   only if the reference tools are clearly better on several files.
   (pdfium needs a native library download, which means a fetch name and
   consent; that's a real cost.)
9. **Write it down** in `docs/research/vietnamese-pdf-spike.md`: the table
   (without private content), the decision, and fixtures (public files
   only) for tests.

### G.5 Edge cases

- **NFC changes text length** (fewer code points). Character offsets in
  imported passages are not stored, so nothing breaks.
- **NFC on code blocks**: harmless (ASCII is unchanged).
- **Compatibility forms** (NFKC would turn "ﬁ" into "fi", full-width into
  ASCII): don't use NFKC. It changes meaning in technical text (`²` → `2`).
- **G-2 on very short chunks** (< 20 letters): the 2% rule is too noisy.
  Require ≥ 2 Vietnamese-only letters as well.
- **Mixed documents**, half English and half Vietnamese: detection is per
  chunk, which is right.

### G.6 How to test

- Unit (`readers.rs`): an NFD Markdown file reads back as NFC; `normalize`
  is idempotent.
- Unit (store + sync): a project synced with reader version 1, then synced
  with version 2 → NFD documents upserted and counted in `reread`,
  NFC documents untouched, `content_hash` unchanged.
- Unit (`lang.rs`): the table in G.1 as fixtures, with expected results
  after G-2 (Redis → vi, Kubernetes → vi, token bucket → none, French →
  fr, "tang timeout nginx" → none). Extend `detects_vietnamese_and_english`
  (`lang.rs:129-139`).
- CLI: `vietnamese_names_and_queries_print_intact` (`cli.rs:1298`) plus an
  NFD document whose real query (typed NFC, with `text`) imports.
- Real: the PDF spike.

| Item | Effort | Risk |
|---|---|---|
| G-1 NFC + reader version | S (2–3 days) | Medium: one dataset re-key (training reruns once; LLM calls only for changed chunks) |
| G-2 Vietnamese-letter rule | S (1 day) | Low–medium: changes some chunks' language, so some queries are re-asked |
| G-3 TCVN3 skip | S, after evidence | Low |
| G-4 no-diacritics slice | S (2 days) | Low |

## I. Smaller items

### I.1 The style pool silently re-asks the LLM for every chunk

**Problem.** The style examples are part of the generator's cache key
(`generator.rs:476-487`, `"style": self.style`). The pool is "one in four,
at most five, picked by hash" of *all* live real queries
(`dataset.rs:230-239`). Importing 4 more real queries can change which
queries are in the pool, which changes the key, which makes **every chunk**
a cache miss. On a CPU that is hours. The dry run says "settings changed
since the last dataset" (`graph.rs:752-756`) and shows the LLM calls, but
not why.

**Options:**

1. **Freeze the pool (recommended).** New migration: `ALTER TABLE
   real_queries ADD COLUMN style INTEGER NOT NULL DEFAULT 0`. The first
   time ≥ 4 live real queries exist, pick the pool by today's rule and
   mark it. Later imports never change it. `synk queries import --restyle`
   re-picks on purpose, and the dry run then says "style examples changed:
   312 chunks re-asked". A style query removed by `--replace` leaves the
   pool smaller until `--restyle`.
2. Drop style from the per-chunk cache key, keep it in the dataset key:
   cheap, but cached queries from the old style would mix with new ones,
   so a dataset no longer means "these style examples".
3. Only warn. Leaves the trap.

**Surface:** `synk queries list --json` adds `style: true|false` per query
(add-only). The dry-run dataset step adds the reason `"style examples
changed"` when the generator key differs only in style. Bump
`PROMPT_VERSION`: no (the prompt doesn't change).

**Test:** import 8 queries, build a dataset, import 4 more → `train
--dry-run` shows `llm_calls == 0` and the same pool.

**Effort:** S (1 day). Must ship with or before `queries template` (B).

### I.2 The torch install step isn't pinned in time

**Problem.** The torch step installs `torch==2.14.1` from the PyTorch
index with no `--exclude-newer` (`sidecar.rs:428-432`), while the next step
uses it (`sidecar.rs:434-443`). Torch's own dependencies (filelock, sympy,
networkx, jinja2, …) therefore resolve to whatever is newest on the
PyTorch index on the day you install. The comment at `sidecar.rs:20-21`
promises the opposite.

**Tested** (`uv 0.13.1`, Windows, CPU index):

- As today: resolves (`filelock==3.32.3`, from the PyTorch index's mirror).
- **Adding `--exclude-newer 2026-10-14T00:00:00Z` as the survey suggested:
  fails** ("No solution found … `filelock` was filtered by
  `exclude-newer`"). The PyTorch index's files are filtered out by the
  date rule.
- **Works:** `--default-index https://pypi.org/simple --index
  https://download.pytorch.org/whl/cpu --index-strategy unsafe-best-match
  --exclude-newer 2026-10-14T00:00:00Z --exclude-newer-package torch=false`
  resolved `torch==2.14.1+cpu` with its dependencies from PyPI as of the
  date (`filelock==4.1.1`). uv documents that `exclude-newer-package` with
  `false` exempts a package
  ([uv settings](https://docs.astral.sh/uv/reference/settings/#exclude-newer)).
  `unsafe-best-match` lets PyPI and the PyTorch index compete for every
  package. That is acceptable here only because torch is pinned exactly
  and the rest is date-capped **[review the dependency-confusion trade-off
  before adopting]**.

**Options:**

1. **A lock file per backend and OS (recommended).** At release time, `uv
   pip compile --generate-hashes` the whole environment for each
   (backend, OS, arch). Ship the files in the binary. Install with `uv pip
   install --require-hashes -r <lock>`. Every install is byte-identical and
   verified, and resolution never happens on the user's machine.
2. The tested command above. A one-line fix, but resolution still happens
   on the user's machine.

**Effort:** option 2 is S (½ day, plus re-testing CUDA and macOS). Option 1
is S–M (2–3 days: a release script and 5–6 lock files). Both change the
environment recipe, so the env name hash changes (`sidecar.rs:382-390`) and
users rebuild the trainer once (a 1–3.5 GB download that needs consent:
`synk fetch trainer` will list it).

## Decisions for the owner

1. **Default `test_percent`: keep 20, or make `"auto"` the default?**
   - *Keep 20, auto opt-in*: no surprise for anyone; small corpora keep
     getting useless tests unless they read the advice.
   - *Auto by default* (**recommended**): projects with ≥ ~50 documents
     get the identical split (and keys); small projects get 3–10 test
     documents instead of 1–2, at the cost of training documents.
     Revisit when folds land.
2. **Cross-validation in v0.2 or v0.3?** *v0.2*: the full fix for small
   corpora now, but the release grows by 1–2 weeks and a run then owns K+1
   models. *v0.3* (**recommended**): ship the warning, auto and real-query
   template first; build folds on top of the OS lock and Ctrl-C work.
3. **GGUF converter: vendor, fetch name, or drop?** **Recommend vendoring**
   (no download, same update burden as today, ~2 MB). Sub-choice: commit
   the zip, or zip in `build.rs` (**recommend `build.rs`**: diffs stay
   readable).
4. **When real queries decide.** Recommend **≥ 30 queries and ≥ 10
   documents**, with an `EVAL_VERSION` bump; alternatives: keep ≥ 2
   documents (today), or 5.
5. **Exit code on Ctrl-C**: **130** (recommended; shell convention) or 1
   (today's "everything else"). Either way stdout still carries one
   `CANCELLED` object.
6. **Disk check strictness**: block when `free < estimate`
   (**recommended**, with `SYNK_DISK_CHECK=warn` as the escape hatch), or
   warn only until estimates are measured.
7. **New dependencies**: `ctrlc` (with `termination`) and `fs4` —
   **recommend both**. For the Windows job object: `process-wrap` (one
   crate for both OSes) or ~50 lines of `windows-sys` FFI —
   **recommend `process-wrap`** unless dependency count matters more.
8. **Template file format**: JSONL (**recommended**, the importer reads it)
   or also CSV for spreadsheet users (later, if asked).
9. **One dataset re-key in v0.2.** NFC (`reader`), sampling and auto split
   all change dataset keys, so the first `synk train` after upgrading
   retrains (LLM queries stay cached; only NFD or re-detected chunks are
   re-asked). **Recommend accepting it once**, bumping `KIND_VERSION` once,
   and saying so in the release notes. The alternative (params that appear
   only when something changed) avoids the retrain for most projects but
   is harder to reason about for NFC.
10. **Torch pin**: lock files (**recommended**, reproducible and verified)
    or the tested `--exclude-newer-package torch=false` flags (quick).
    Either one makes users rebuild the trainer once.

## Glossary of new terms

Plain words, in the style of `GLOSSARY.md`.

**Test document**:
A document held out of training and used only to test. All its chunks and
their queries are in the test split. The verdict counts test documents,
not test queries, because queries about one document rise and fall
together.
_Avoid_: test file, eval doc

**Fold**:
One of K equal groups of documents in cross-validation. Each fold is held
out once while a model trains on the others, so every document is tested
once by a model that never saw it.
_Avoid_: split (that's train/test), partition

**Real query**:
A search a person wrote, imported with `synk queries import`. Never used
for training. It tests the tuned model on the whole corpus, the way you
will use it. With 30 or more covering at least 10 documents, real queries
decide the verdict.
_Avoid_: human query, gold query

**Synthetic query**:
A search written by the LLM from a chunk. Training uses them, and so does
the test on held-out documents. Because the same LLM writes both, a gain
on them partly means "better at this LLM's style".
_Avoid_: generated question

**Power**:
How often the test would say `better` if tuning truly improved search by a
given amount. 80% is the usual target. Power grows with the number of test
documents.
_Avoid_: sensitivity, confidence

**Smallest detectable change**:
The true improvement in search quality (nDCG@10) the test catches 8 times
out of 10. If it is larger than the gains tuning usually brings (~0.05),
the test is too small to give a verdict. Shown as
`min_detectable_delta`.
_Avoid_: margin of error, minimum effect

**Refit**:
Training once more on all documents, test documents included, with the
settings a run (or cross-validation) already tested. The refit model has
no held-out score of its own; its promise rests on the earlier test, and
synk labels it so.
_Avoid_: retrain (too vague), final model

**Template** (queries):
A file `synk queries template` writes, with one line per chosen document
and an empty search for you to fill in without opening the document.
_Avoid_: form, questionnaire

**Reader version**:
A number that changes when synk changes how it turns files into text.
When it changes, the next sync re-reads every file once.
_Avoid_: parser version
