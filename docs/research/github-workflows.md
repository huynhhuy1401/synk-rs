# How should synk build, test, lint and release with GitHub Actions?

Checked: 2026-10-16. Status: research + recommendation, not accepted.

Sources are primary (GitHub Docs, the actions' own repos and source, the dist
book and source, rust-lang docs, Hugging Face docs, PyPI) unless marked.
**[unverified]** = I could not confirm it against a primary source.

## TL;DR

- **Add three files and keep the generated one.** `ci.yml` (fmt, clippy,
  tests on Linux, Windows and macOS, MSRV, advisories), `e2e.yml` (the real
  training test, weekly and by hand), `dependabot.yml`. Keep
  `release.yml` generated by dist. Never edit it by hand.
- **It costs nothing.** Standard GitHub-hosted runners are free and unlimited
  for public repos, macOS included.
- **The existing release setup is correct but one version behind.** The
  committed `release.yml` matches dist 0.32.0 exactly (`dist generate --check`
  passes). dist 0.33.0 is out (2026-09-10). Upgrade with `dist selfupdate`.
- **Drop `x86_64-apple-darwin` from the release targets.** PyTorch 2.14.1 has
  no Intel-Mac wheels, so `synk setup` can't build a trainer there. We would
  ship a binary we can't test and that can't train.
- **Turn on dist's GitHub attestations.** It's one config line and free for
  public repos.
- **Don't publish to crates.io yet.** It would mean publishing all five
  crates, and users already get prebuilt binaries from the installers.

## 1. What the repo has today

- **`.github/workflows/release.yml`.** It's generated by dist 0.32.0 (the
  header says "autogenerated by dist"). It runs `dist plan` on every pull
  request. On a version tag it builds and uploads a GitHub Release.
  `dist generate --check` reports no difference on this checkout, so the
  file hasn't been hand-edited.
- **`dist-workspace.toml`.** `cargo-dist-version = "0.32.0"`, `ci = "github"`,
  shell and powershell installers, `install-path = "CARGO_HOME"`, no updater,
  five targets, GitHub hosting.
- **`dist plan` output.** It plans one app, `synk 0.1.0`, with one archive
  per target, `synk-installer.sh`, `synk-installer.ps1`, a `.sha256` file per
  archive, a unified `sha256.sum` and `source.tar.gz`. Each archive has only
  `README.md` in it. **There are no LICENSE files in the repo.** The
  workspace says `MIT OR Apache-2.0`, but no license text ships. dist picks up
  `LICENSE*` files automatically
  ([archives](https://github.com/axodotdev/cargo-dist/blob/v0.33.0/book/src/artifacts/archives.md)).
- **There is no CI workflow and no `rust-toolchain.toml`.**
- **Native (C) code in the build:**
  - `rusqlite` uses `features = ["bundled"]`. That compiles SQLite from C
    with `cc`
    ([libsqlite3-sys Cargo.toml](https://github.com/rusqlite/rusqlite/blob/v0.32.1/libsqlite3-sys/Cargo.toml)).
  - `ureq` 3 defaults to rustls with `ring` and webpki roots
    ([ureq Cargo.toml](https://github.com/algesten/ureq/blob/main/Cargo.toml)).
    So there's no OpenSSL. `Cargo.lock` has `rustls` and `ring`, and no
    `openssl-sys` or `native-tls`.
  - Per `Cargo.lock`, the only crates that depend on `cc` are `blake3`,
    `libsqlite3-sys` and `ring`. `tokenizers` is built with
    `default-features = false`, and `esaxx-rs` has no dependencies in the
    lockfile, so it's pure Rust.
- **Declared MSRV is `rust-version = "1.88"`, edition 2024.** The highest
  `rust-version` among locked dependencies is 1.88 (`zip` 9.0.3), from
  `cargo metadata`. Nobody checks that synk's own code builds on 1.88.
- **The real end-to-end test** is `train_evaluates_and_exports` in
  `crates/synk/tests/cli.rs`. It's `#[ignore]`d and reads `SYNK_E2E_PYTHON`.
  It downloads the base model, the `mmarco-minilm-l12` reranker and the
  general check's sets. Model revisions are pinned in
  `crates/synk-pipeline/catalog.toml`. It uses `HF_HUB_CACHE`, then
  `HF_HOME/hub`, then `~/.cache/huggingface/hub` (`hub.rs`). The trainer env
  comes from `synk setup`: Python 3.12, `torch==2.14.1`,
  `sentence-transformers[train]==6.1.0` and extras, with uv
  `--exclude-newer 2026-10-14` (`sidecar.rs`). `synk setup --json` prints
  the interpreter path as `data.python`.

## 2. CI on push and pull request

### Runners, cost and limits

- **Labels that exist now**
  ([GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)):

  | Runner | Labels | CPU / RAM / SSD |
  |---|---|---|
  | Linux x64 | `ubuntu-latest` (= 24.04), `ubuntu-22.04`, `ubuntu-24.04`, `ubuntu-26.04` | 4 / 16 GB / 14 GB |
  | Linux arm64 | `ubuntu-22.04-arm`, `ubuntu-24.04-arm`, `ubuntu-26.04-arm` | 4 / 16 GB / 14 GB |
  | Windows x64 | `windows-latest` (= 2025), `windows-2025`, `windows-2022` | 4 / 16 GB / 14 GB |
  | Windows arm64 | `windows-11-arm` | 4 / 16 GB / 14 GB |
  | macOS arm64 (M1) | `macos-latest` (= macOS 26), `macos-14`, `macos-15`, `macos-26` | 3 / 7 GB / 14 GB |
  | macOS Intel | `macos-15-intel`, `macos-26-intel` | 4 / 14 GB / 14 GB |

- **Free for public repos.** "Use of the standard GitHub-hosted runners is
  free and unlimited on public repositories"
  ([runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners),
  [billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions)).
  That includes macOS and the arm64 runners. So yes: macOS can be verified in
  CI for free.
- **Limits** ([limits](https://docs.github.com/en/actions/reference/limits)):
  - 6 hours per job.
  - 20 concurrent jobs on the Free plan, at most 5 of them macOS.
  - 10 GB of cache per repo. Caches not used for a week are evicted
    ([actions/cache](https://github.com/actions/cache)).
- **Intel macOS is ending.** `macos-15-intel` was announced as the last
  x86_64 image, with support ending after August 2027
  ([runner-images#13045](https://github.com/actions/runner-images/issues/13045)).
  A `macos-26-intel` label is now listed too.

### What to run

These come straight from AGENTS.md:

- `cargo fmt --all --check`
- `cargo clippy --all-targets --locked -- -D warnings`. Pass `-D warnings`
  to clippy only. Don't set it in `RUSTFLAGS`, because that changes the build
  cache key.
- `cargo test --locked`. The suite uses `SYNK_FAKE_TRAINER=1` and a private
  `SYNK_HOME`, so it needs no Python and no network (`cli.rs` header).

Run clippy and tests on all three OSes. The code has `cfg(windows)` branches
(for example, uv and venv paths in `sidecar.rs`). Linux and Windows cover
both sides of those branches. macOS is the platform nobody runs today.

The owner develops on Windows. Expect the first Linux and macOS runs to
surface a few path or line-ending failures. That is the point of running
them.

### Toolchain: `rustup` directly, no `rust-toolchain.toml` for now

- **Rust is already on every runner image.** Ubuntu 24.04 and Windows 2025
  ship Rust 1.99.0. macOS 15 arm64 ships 1.98.1
  ([Ubuntu](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md),
  [Windows](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md),
  [macOS 15 arm64](https://github.com/actions/runner-images/blob/main/images/macos/macos-15-arm64-Readme.md)).
  Images don't all ship the same version. So CI should run
  `rustup toolchain install stable` first, and every OS then lints with the
  same clippy. The cargo book's own example does this with plain `rustup`
  commands
  ([cargo CI guide](https://doc.rust-lang.org/cargo/guide/continuous-integration.html)).
- **`dtolnay/rust-toolchain` is fine but not needed.** It picks the
  toolchain from the `@rev` you use. If you pin it by SHA, you must use a
  commit on `master` and pass `toolchain:`. Commits on other branches get
  garbage-collected
  ([README](https://github.com/dtolnay/rust-toolchain)). Calling `rustup`
  directly means one fewer third-party action to trust and pin.
- **`rust-toolchain.toml` pins the toolchain for everyone.** That's local
  dev, CI and dist's release build, since rustup reads it before the default
  toolchain
  ([rustup overrides](https://rust-lang.github.io/rustup/overrides.html)).
  - Upside: reproducible lints.
  - Cost: the owner has to bump it by hand. Dependabot doesn't manage it.
  - For a solo project, tracking `stable` is simpler. The risk is that a
    new stable release adds a clippy lint that fails `-D warnings`. When that
    happens, fix the lint or `#[allow]` it. If it happens often, add
    `rust-toolchain.toml` then.

### MSRV check: cheap, worth one job

- **Cargo enforces `rust-version`.** If the toolchain is older, Cargo reports
  an error to the user
  ([rust-version](https://doc.rust-lang.org/cargo/reference/rust-version.html)).
  So `1.88` is a promise to anyone who runs `cargo install --git`.
- **The cargo book suggests one job, on one platform, with `cargo check`**
  ([cargo CI guide](https://doc.rust-lang.org/cargo/guide/continuous-integration.html)).
  Its example uses `cargo hack check --rust-version --ignore-private`. That
  skips crates that aren't published, which would skip everything here if
  you later set `publish = false`. So use plain `cargo check` on the 1.88
  toolchain.
- **The alternative is to delete `rust-version`.** Don't keep a number
  nothing checks.

### Build cache: `Swatinem/rust-cache`, not sccache

- **rust-cache stores `~/.cargo` and `./target` dependency artifacts.** The
  key includes the rustc version and hashes of `Cargo.lock` and
  `Cargo.toml`. It doesn't cache workspace crates. It sets
  `CARGO_INCREMENTAL=0`. Inputs: `save-if`, `shared-key`, `cache-on-failure`
  ([README](https://github.com/Swatinem/rust-cache)). Install the toolchain
  before this step, because the key uses the current rustc.
- **Save only from `main`.** Use `save-if: ${{ github.ref == 'refs/heads/main' }}`.
  Pull requests can read caches from the default branch
  ([actions/cache](https://github.com/actions/cache)). This keeps PR caches
  from crowding the 10 GB limit.
- **sccache is a compiler wrapper with its own limits.** It can't cache
  crates that call the system linker (bin, proc-macro) or incrementally
  compiled crates. By default it needs matching absolute paths
  ([sccache](https://github.com/mozilla/sccache)). It helps big multi-repo
  setups, not a five-crate workspace. Skip it.

### Concurrency

- Use `group: ${{ github.workflow }}-${{ github.ref }}` with
  `cancel-in-progress`
  ([concurrency](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)).
- The docs warn that with a plain `true`, a new push to `main` cancels the
  run already in progress. Set
  `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`. That
  cancels superseded PR runs and lets every `main` commit finish.

### Permissions: least privilege

- **Give `GITHUB_TOKEN` read-only contents by default, and raise it per job
  only when needed**
  ([secure use](https://docs.github.com/en/actions/reference/security/secure-use)).
  For CI, `permissions: contents: read` at the top is enough.
- **Use `persist-credentials: false` on checkout.** zizmor's `artipacked`
  audit flags the default
  ([zizmor audits](https://docs.zizmor.sh/audits/)). dist's `release.yml`
  already does this.
- **Never use `pull_request_target`** for this repo
  ([secure use](https://docs.github.com/en/actions/reference/security/secure-use)).

### Pinning actions: by SHA, with a version comment

- **GitHub recommends pinning to a full commit SHA.** "Pin actions to a tag
  only if you trust the creator", because tags can be moved
  ([secure use](https://docs.github.com/en/actions/reference/security/secure-use)).
  zizmor's default `unpinned-uses` policy, since v1.20.0, requires SHA pins
  on all actions, `actions/*` included
  ([zizmor audits](https://docs.zizmor.sh/audits/)).
- **Dependabot keeps the pins current.** It updates the `# vX.Y.Z` comment
  when the comment is on the same line
  ([changelog 2022-10-31](https://github.blog/changelog/2022-10-31-dependabot-now-updates-comments-in-github-actions-workflows-referencing-action-versions/)).
  Caveat: Dependabot *alerts* don't cover SHA-pinned actions. Version updates
  do.
- **New option: workflow lockfiles.** These went into public preview on
  2026-10-14, for Free plans too
  ([changelog](https://github.blog/changelog/2026-10-14-github-actions-workflow-lockfiles-in-public-preview/),
  [how-to](https://docs.github.com/en/actions/how-tos/secure-your-work/lock-workflow-dependencies)).
  - `gh extension install github/gh-actions-lock`, then `gh actions-lock`,
    writes `.github/workflows/actions.lock`.
  - It pins actions and their transitive dependencies to commits.
    Dependabot regenerates the entries.
  - GitHub says it "supersedes SHA pinning" for repos that adopt it.
  - It's two days old and "subject to change". Revisit it later. SHA pins
    are the safe choice today.
- **SHAs used below** come from `git ls-remote` on 2026-10-16, peeled to
  commits:

  | Action | Version | Commit |
  |---|---|---|
  | actions/checkout | v7.0.1 | `3d3c42e5aac5ba805825da76410c181273ba90b1` |
  | Swatinem/rust-cache | v2.9.2 | `6323deb102c322ba6fcbdcafc7e3dddab59af2b6` |
  | astral-sh/setup-uv | v10.3.0 | `1c37ad07a6a961277cf70c0d37d6f313000f5884` |
  | actions/cache | v6.1.0 | `55cc8345863c7cc4c66a329aec7e433d2d1c52a9` |
  | taiki-e/install-action | v2.87.28 | `1168f6810a3cb30a3514bf5756a3b7f0422c6df8` |
  | zizmorcore/zizmor-action | v0.7.1 | `85b2b9fb8e3325e7a23d7d0a9d7ba5ae0f999e3e` |

### Dependabot

- **Ecosystems:** `github-actions` (with `directory: "/"`, it scans
  `.github/workflows`) and `cargo`
  ([options reference](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/dependabot-options-reference),
  [actions guide](https://docs.github.com/en/code-security/dependabot/working-with-dependabot/keeping-your-actions-up-to-date-with-dependabot)).
- **`groups` with `patterns`** puts matching updates in one PR.
- **`cooldown`** delays version updates. There's a default of 3 days even
  without config. Security updates are never delayed. zizmor has a
  `dependabot-cooldown` audit.
- **Problem: Dependabot would edit `release.yml`.** dist treats any edit or
  out-of-date content in `release.yml` as an error
  ([customizing CI](https://github.com/axodotdev/cargo-dist/blob/v0.33.0/book/src/ci/customizing.md)).
  The PR's `dist plan` run would then fail.
  - Exclude the file with `exclude-paths`. The docs describe it per
    ecosystem but don't list which ecosystems support it **[unverified for
    `github-actions`]**.
  - If Dependabot still opens a PR against `release.yml`, close it. dist
    bumps its own actions when you upgrade dist. For example, 0.30.4 and
    0.32.0 "bump default github actions"
    ([dist CHANGELOG](https://github.com/axodotdev/cargo-dist/blob/main/CHANGELOG.md)).
- **What Dependabot won't see:** the Python pins in `sidecar.rs` are Rust
  string constants. Bumping torch and sentence-transformers stays a manual
  job, which suits the "only what we can test" policy.

## 3. The real end-to-end test in CI

### Feasible? Yes, on Linux and macOS arm64, CPU only

- **Time:** 6 h job limit. The test takes about 12 min on the owner's CPU.
  On a 4-vCPU Linux runner, with a cold env, expect 20 to 40 min in total
  **[unverified, estimate]**. Set `timeout-minutes: 120`.
- **Disk:** 14 GB SSD. The CPU torch env plus small models fits
  comfortably. Exact size **[unverified]**.
- **Wheels exist:**
  - PyPI has `torch==2.14.1` cp312 wheels for `macosx_14_0_arm64`,
    `manylinux_2_28_aarch64`, `manylinux_2_28_x86_64` and `win_amd64`. There
    is **no macOS x86_64 wheel**
    ([PyPI JSON](https://pypi.org/pypi/torch/2.14.1/json)).
  - The CPU index `download.pytorch.org/whl/cpu` has the same, including the
    macOS arm64 wheel
    ([index](https://download.pytorch.org/whl/cpu/torch/)).
  - PyTorch stopped building macOS x86_64 after 2.2
    ([RFC #114602](https://github.com/pytorch/pytorch/issues/114602)).
  - So `synk setup --backend cpu` can work on `ubuntu-latest`,
    `macos-latest` (macOS 26 ≥ 14) and `windows-latest`, and **cannot work
    on any Intel Mac**.
- **macOS arm64 runners have only 3 cores and 7 GB RAM.** That's enough for
  `multilingual-e5-small` with `batch_size = 2`, but slower. The runner docs
  don't mention MPS. synk doesn't use MPS anyway (ADR 0003).
- **Cost:** free (public repo).
- **This verifies the CPU path only. GPU stays manual on Kaggle**, as ADR
  0003 says.

### When to run it

Don't run it on every PR. Run it:

1. On a weekly `schedule`.
2. By hand with `workflow_dispatch`, always once before tagging a release.
3. On pushes to `main` that touch `crates/synk-pipeline/**`.

Two things to know about schedules
([events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)):

- They run only on the default branch, and can be delayed at busy times,
  especially at the start of the hour. Use an odd minute.
- In a public repo they are **disabled after 60 days without repo
  activity**.

### Caching the trainer env and the models

- **The uv cache and the managed Python: `astral-sh/setup-uv`.**
  - Set `enable-cache: true`. With the default `auto`, caching is on for
    most events but off for release, tag-push, `pull_request_target` and
    `workflow_run`.
  - Set `cache-dependency-glob` to `crates/synk-pipeline/src/sidecar.rs`,
    the file that holds the pins. The cache resets whenever the recipe
    changes.
  - `cache-python: true` uploads uv-managed Pythons.
  - `prune-cache` defaults to `false`
    ([action.yml v10.3.0](https://github.com/astral-sh/setup-uv/blob/v10.3.0/action.yml),
    [caching docs](https://github.com/astral-sh/setup-uv/blob/main/docs/caching.md)).
  - uv's own advice is `uv cache prune --ci`. That drops pre-built wheels,
    because re-downloading is often faster
    ([uv cache](https://docs.astral.sh/uv/concepts/cache/)). Leave pruning
    off here: the torch wheel is the big download, and keeping it is the
    point. With a warm cache, `synk setup` still rebuilds the venv, but from
    local files.
- **Hugging Face downloads: `actions/cache` on `~/.cache/huggingface`.**
  - That's the default `HF_HOME`, and `HF_HUB_CACHE` defaults to
    `$HF_HOME/hub`
    ([HF env vars](https://huggingface.co/docs/huggingface_hub/package_reference/environment_variables)).
    synk's `hub.rs` uses the same default.
  - Key the cache on `hashFiles('crates/synk-pipeline/catalog.toml')`,
    since revisions are pinned there.
  - A weekly run sits right at the 7-day eviction edge, so expect some cold
    runs. That's fine.
- **Rate limits:** anonymous Hub downloads ("resolvers") are allowed 3,000
  per 5 minutes per IP. Free accounts get 5,000. HF's first advice when
  rate-limited is to pass `HF_TOKEN`
  ([rate limits](https://huggingface.co/docs/hub/rate-limits)).
  - Runner IPs are shared. If you see 429s, add a read-only `HF_TOKEN`
    repository secret and pass it to the test step.
  - Don't wire in an empty secret by default. `hub.rs` sends `HF_TOKEN`
    "when set", and whether an empty value counts as set is
    **[unverified]**.

## 5. Release

### The dist setup

- **Version.** The repo pins `cargo-dist-version = "0.32.0"` (2026-05-21).
  The latest stable is **0.33.0** (published 2026-09-11)
  ([releases](https://github.com/axodotdev/cargo-dist/releases)). A
  `v1.0.0-rc.1` tag exists with no published release. Wait for 1.0 final.
  0.33.0 adds:
  - Windows signing through Azure. Not needed here.
  - It moves the shell installer's `env` script into the app config dir.
    Existing installs are migrated.
  - The attestation `--repo` fix.
- **Don't hand-edit `release.yml`.** "Since 0.3.0 we will actually consider
  it an error for there to be any edits or out of date information in
  release.yml". `allow-dirty = ["ci"]` opts out, at the cost of losing
  `dist init` updates
  ([customizing CI](https://github.com/axodotdev/cargo-dist/blob/v0.33.0/book/src/ci/customizing.md)).
  Change behaviour through `dist-workspace.toml`, then regenerate.
- **Regenerating** ([CLI](https://axodotdev.github.io/cargo-dist/book/reference/cli.html),
  [updating](https://axodotdev.github.io/cargo-dist/book/updating.html)):
  - `dist selfupdate` updates dist, then runs `init`.
  - `dist init` sets up or updates and regenerates CI. Run it without `-y`
    so it offers new features.
  - `dist generate` rewrites `release.yml` from config. `--check` only
    reports differences.
  - `dist plan` shows what a release would build, without building.
- **PR behaviour.** `pr-run-mode` defaults to `"plan"`: every PR runs
  `dist plan`, which is quick. That also catches a stale `release.yml`.
  Keep it.
- **Runners dist uses** (source,
  [github.rs v0.33.0](https://github.com/axodotdev/cargo-dist/blob/v0.33.0/cargo-dist/src/backend/ci/github.rs)):

  | Target | Runner |
  |---|---|
  | `x86_64-unknown-linux-gnu` | `ubuntu-22.04` |
  | `aarch64-unknown-linux-gnu` | `ubuntu-22.04-arm`, native ([0.30.0](https://github.com/axodotdev/cargo-dist/blob/main/CHANGELOG.md)) |
  | `aarch64-apple-darwin` | `macos-14` |
  | `x86_64-apple-darwin` | `macos-15-intel` |
  | Windows | `windows-2022` |

  **So aarch64 Linux isn't cross-compiled.** The C code in bundled SQLite,
  ring and blake3 builds natively. No cross toolchain is needed.
- **Installers and checksums.** The shell and powershell installers are
  already configured. `checksum` defaults to sha256: one file per archive,
  plus a unified `sha256.sum` you can check with `sha256sum -c`
  ([checksums](https://github.com/axodotdev/cargo-dist/blob/v0.33.0/book/src/artifacts/checksums.md)).
  Nothing to change.
- **Homebrew.** It needs `installers = [..., "homebrew"]`, a separate tap
  repo that already exists, and a token with write access to it
  ([config](https://axodotdev.github.io/cargo-dist/book/reference/config.html)).
  That's an extra repo and a secret to look after, for a platform that is
  only now getting CI. Skip it until macOS users ask. The shell installer
  already works on macOS.
- **Intel Mac target.** `x86_64-apple-darwin` builds fine, but no
  torch 2.14.1 wheel exists for it (section 3). Under "support only what we
  can test", remove it from `targets`. Re-add it only if synk gains a
  trainer that doesn't need PyTorch wheels.

### glibc vs musl

- **Linux builds run on `ubuntu-22.04`, which has glibc 2.35**
  ([packages.ubuntu.com](https://packages.ubuntu.com/jammy/libc6)). The
  binaries need glibc 2.35 or newer. Exact symbol versions used:
  **[unverified]**.
- **The trainer has its own floor.** The torch wheels are
  `manylinux_2_28`, so the Python side needs glibc ≥ 2.28 anyway.
- **dist supports static musl targets** (`x86_64-unknown-linux-musl`,
  `aarch64-unknown-linux-musl`)
  ([config](https://axodotdev.github.io/cargo-dist/book/reference/config.html)).
  A musl binary would run on older or Alpine systems, but torch has no musl
  wheels. So synk couldn't train there, and musl adds a target nobody
  tests. **Stay on glibc.**

### Tag-driven flow

dist's quickstart is: bump the version, commit, then
`git tag v0.1.0 && git push --tags`
([quickstart](https://axodotdev.github.io/cargo-dist/book/quickstart/rust.html)).
The tag must match the workspace version. Prerelease suffixes such as
`v0.2.0-rc.1` become GitHub prereleases (see the `release.yml` header).

Release checklist for a solo maintainer:

1. CI is green on `main`.
2. Run E2E by hand (Actions → E2E → Run workflow). Wait for green.
3. Bump `version` in `[workspace.package]` and the four
   `[workspace.dependencies]` `version = "…"` entries. Move the `Unreleased`
   changelog section under the new version. Commit.
4. `git tag vX.Y.Z && git push origin main vX.Y.Z`.

### Changelog: a manual `CHANGELOG.md`

- **dist reads a top-level `CHANGELOG*`/`RELEASES*` file.** It finds the
  heading for the version being released (via `parse-changelog`) and uses it
  for the GitHub Release title and body. A `# Unreleased` heading also works
  for prereleases
  ([simple guide](https://github.com/axodotdev/cargo-dist/blob/v0.33.0/book/src/workspaces/simple-guide.md)).
  It also puts `CHANGELOG*` in each archive
  ([archives](https://github.com/axodotdev/cargo-dist/blob/v0.33.0/book/src/artifacts/archives.md)).
- **release-plz** opens a release PR, writes a changelog with git-cliff,
  publishes to a cargo registry, and creates tags and GitHub releases
  ([docs](https://release-plz.dev/docs)). Its main value is crates.io
  publishing. Its own GitHub release would collide with dist's, and its
  docs don't describe running alongside dist
  ([binaries page](https://release-plz.dev/docs/extra/releasing-binaries)).
  **Skip it.**
- **git-cliff** only drafts a changelog from commit messages, which works
  best with conventional commits. It's optional, and you can run it locally
  (`taiki-e/install-action` can install it). **Start manual.**

### crates.io: no, for now

- **crates.io rejects path-only dependencies.** Each internal crate
  (`synk-core`, `synk-store`, `synk-connectors`, `synk-pipeline`) would
  have to be published first, in order
  ([specifying dependencies](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html)).
  That's five crate names reserved forever, and five publishes per release.
  None of the names are taken today (crates.io API, 2026-10-16).
- **Users don't need it.** The one-line installers give prebuilt binaries
  with no Rust needed. That's what README.md already documents.
- **Guard against an accidental `cargo publish`.**
  - Set `publish = false` on the four library crates
    ([manifest](https://doc.rust-lang.org/cargo/reference/manifest.html)).
  - **Careful with `crates/synk`.** dist reads `publish = false` as a
    signal not to distribute a package. If you set it there, also set
    `dist = true` for that package
    ([config `dist`](https://github.com/axodotdev/cargo-dist/blob/v0.33.0/book/src/reference/config.md)).
    For a Cargo package, that goes in `[package.metadata.dist]`.
  - The library crates have no binaries, so dist ignores them either way.
  - Run `dist plan` after the change to confirm `synk` is still listed.
- **Later:** if you want `cargo install synk`, release-plz is the tool for
  publishing the workspace in order.

## 6. Recommendation

Keep it to **four workflow-related files**:

| File | Who writes it | Runs on |
|---|---|---|
| `.github/workflows/ci.yml` | by hand (below) | push to `main`, every PR, manual |
| `.github/workflows/release.yml` | **dist only** | PRs (`dist plan`), version tags (release) |
| `.github/workflows/e2e.yml` | by hand (below) | weekly, manual, `main` pushes touching the pipeline |
| `.github/dependabot.yml` | by hand (below) | weekly |

Optional fifth: a zizmor job, shown at the end. Add it once the rest is
green.

### Steps, in order

1. **Add LICENSE files.** Add `LICENSE-MIT` and `LICENSE-APACHE` at the
   repo root so archives carry the license text. dist auto-detects
   `LICENSE*`. With two matching files, which one dist includes is
   **[unverified]**. Check `dist plan` after adding them.
2. **Upgrade dist and regenerate `release.yml`** (from the repo root, on
   Windows):

   ```powershell
   dist selfupdate          # installs the latest dist (0.33.0), then runs `dist init`
   # or pin exactly:
   # powershell -ExecutionPolicy Bypass -c "irm https://github.com/axodotdev/cargo-dist/releases/download/v0.33.0/cargo-dist-installer.ps1 | iex"
   # dist init
   ```

   In the `dist init` prompts, or by editing `dist-workspace.toml` and then
   running `dist generate`, end up with:

   ```toml
   [dist]
   cargo-dist-version = "0.33.0"
   ci = "github"
   installers = ["shell", "powershell"]
   install-path = "CARGO_HOME"
   install-updater = false
   # x86_64-apple-darwin removed: no PyTorch wheels for Intel Macs, so it can't train or be tested
   targets = ["aarch64-apple-darwin", "aarch64-unknown-linux-gnu", "x86_64-unknown-linux-gnu", "x86_64-pc-windows-msvc"]
   hosting = "github"
   # Signed build provenance; users check with `gh attestation verify <file> --repo huynhhuy1401/synk-rs`
   github-attestations = true
   ```

   Then check and commit:

   ```powershell
   dist generate --check    # must print nothing and exit 0
   dist plan                # lists 4 archives, both installers, sha256.sum, and README/LICENSE in each archive
   ```

   Update README.md if it mentions Intel Macs.
3. **Add `ci.yml`, `e2e.yml` and `dependabot.yml`** from below.
4. **Optionally, in repo settings:**
   - Branch protection on `main` requiring the `CI` jobs.
   - Workflow permissions set to "Read repository contents".
   - Add an `HF_TOKEN` secret only if E2E hits 429s.

### `.github/workflows/ci.yml`

```yaml
# Lint and test on every push to main and every pull request.
name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

# The token can only read the repo. No job here needs more.
permissions:
  contents: read

# A new push to a PR cancels that PR's older run. Runs on main always finish.
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

env:
  CARGO_TERM_COLOR: always
  RUST_BACKTRACE: "1"

defaults:
  run:
    shell: bash

jobs:
  fmt:
    name: rustfmt
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - run: rustup toolchain install stable --profile minimal --component rustfmt --no-self-update && rustup default stable
      - run: cargo fmt --all --check

  test:
    name: clippy + test (${{ matrix.os }})
    strategy:
      fail-fast: false # see every OS's result, not just the first failure
      matrix:
        os: [ubuntu-latest, windows-latest, macos-latest] # macos-latest = Apple Silicon
    runs-on: ${{ matrix.os }}
    timeout-minutes: 45
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      # Same stable toolchain on every OS (runner images ship different versions).
      - run: rustup toolchain install stable --profile minimal --component clippy --no-self-update && rustup default stable
      - uses: Swatinem/rust-cache@6323deb102c322ba6fcbdcafc7e3dddab59af2b6 # v2.9.2
        with:
          save-if: ${{ github.ref == 'refs/heads/main' }}
      - run: cargo clippy --all-targets --locked -- -D warnings
      - run: cargo test --locked

  msrv:
    name: build on Rust 1.88 (rust-version)
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      # Keep in sync with rust-version in Cargo.toml.
      - run: rustup toolchain install 1.88 --profile minimal --no-self-update && rustup default 1.88
      - uses: Swatinem/rust-cache@6323deb102c322ba6fcbdcafc7e3dddab59af2b6 # v2.9.2
        with:
          save-if: ${{ github.ref == 'refs/heads/main' }}
      - run: cargo check --workspace --all-targets --locked

  advisories:
    name: security advisories (cargo-deny)
    runs-on: ubuntu-latest
    timeout-minutes: 10
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - uses: taiki-e/install-action@1168f6810a3cb30a3514bf5756a3b7f0422c6df8 # v2.87.28
        with:
          tool: cargo-deny
      - run: cargo deny check advisories
```

What each job does, in plain words:

- **fmt** fails if any file isn't `cargo fmt`-formatted.
- **test** runs clippy, failing on any warning, then the whole test suite.
  It does this on Linux, Windows and an Apple Silicon Mac.
- **msrv** proves the `rust-version = "1.88"` promise still holds.
- **advisories** fails if a locked dependency has a published security
  advisory. When a new advisory lands, this can turn red on a PR that didn't
  cause it. Fix it with `cargo update -p <crate>`.

### `.github/workflows/e2e.yml`

```yaml
# The real training test: builds the Python trainer with `synk setup`,
# downloads the models, trains on CPU, evaluates and exports.
# Too slow for every PR, so it runs weekly, by hand, and when the pipeline changes on main.
name: E2E

on:
  schedule:
    - cron: "23 4 * * 1" # Mondays 04:23 UTC (odd minute: the top of the hour is busy)
  workflow_dispatch:
  push:
    branches: [main]
    paths:
      - "crates/synk-pipeline/**"
      - ".github/workflows/e2e.yml"

permissions:
  contents: read

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  CARGO_TERM_COLOR: always
  RUST_BACKTRACE: "1"
  HF_HUB_DISABLE_TELEMETRY: "1"

defaults:
  run:
    shell: bash

jobs:
  e2e:
    name: real training (${{ matrix.os }}, CPU)
    strategy:
      fail-fast: false
      matrix:
        # Linux x64 and Apple Silicon. Windows is tested by hand by the owner;
        # add windows-latest here to cover it in CI too.
        os: [ubuntu-latest, macos-latest]
    runs-on: ${{ matrix.os }}
    timeout-minutes: 120
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
        with:
          persist-credentials: false
      - run: rustup toolchain install stable --profile minimal --no-self-update && rustup default stable
      - uses: Swatinem/rust-cache@6323deb102c322ba6fcbdcafc7e3dddab59af2b6 # v2.9.2
        with:
          save-if: ${{ github.ref == 'refs/heads/main' }}

      # uv, plus a cache of its downloads (torch is the big one) and of the
      # Python it installs. A new cache starts whenever sidecar.rs (the pins) changes.
      - uses: astral-sh/setup-uv@1c37ad07a6a961277cf70c0d37d6f313000f5884 # v10.3.0
        with:
          enable-cache: true
          cache-dependency-glob: crates/synk-pipeline/src/sidecar.rs
          cache-python: true

      # Models and datasets from Hugging Face. Revisions are pinned in catalog.toml.
      - uses: actions/cache@55cc8345863c7cc4c66a329aec7e433d2d1c52a9 # v6.1.0
        with:
          path: ~/.cache/huggingface
          key: hf-${{ runner.os }}-${{ hashFiles('crates/synk-pipeline/catalog.toml') }}

      - name: Build the trainer environment (synk setup)
        id: setup
        run: |
          python=$(cargo run --locked -q -p synk -- setup --backend cpu --json | jq -r '.data.python')
          echo "Trainer Python: $python"
          echo "python=$python" >> "$GITHUB_OUTPUT"

      - name: Run the real end-to-end test
        env:
          SYNK_E2E_PYTHON: ${{ steps.setup.outputs.python }}
          # If Hugging Face rate-limits the runner (HTTP 429), add a read-only
          # token as a repo secret and uncomment:
          # HF_TOKEN: ${{ secrets.HF_TOKEN }}
        run: cargo test --locked -p synk --test cli -- --ignored train_evaluates_and_exports --nocapture
```

Notes:

- `synk setup` is the consent step for the downloads (ADR 0004), so the
  workflow doesn't need `--yes`.
- `jq` is preinstalled on the Ubuntu and macOS images
  ([macOS 26 arm64](https://github.com/actions/runner-images/blob/main/images/macos/macos-26-arm64-Readme.md)).
- `cargo run` sends build output to stderr, and synk prints exactly one
  JSON object on stdout.

### `.github/dependabot.yml`

```yaml
version: 2
updates:
  # Action pins in our hand-written workflows (SHA + "# vX.Y.Z" comment).
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
    cooldown:
      default-days: 7
    # release.yml belongs to dist. Edits there break `dist plan`;
    # dist bumps its own actions when you upgrade dist.
    exclude-paths:
      - .github/workflows/release.yml
    groups:
      actions:
        patterns: ["*"]

  # Rust dependencies: one grouped PR a week for minor/patch bumps.
  # Majors still come one PR each so they can be reviewed separately.
  - package-ecosystem: cargo
    directory: /
    schedule:
      interval: weekly
    cooldown:
      default-days: 7
    groups:
      cargo-minor-patch:
        patterns: ["*"]
        update-types: [minor, patch]
```

If Dependabot still opens a PR that touches `release.yml`, close it.
`exclude-paths` support for `github-actions` is **[unverified]**.

`.github/zizmor.yml`.

### What this deliberately leaves out

- **GPU CI.** CUDA stays manual on Kaggle (ADR 0003).
- **Intel macOS** (no torch wheels), **musl**, and **Windows arm64**. These
  are untested platforms, so they aren't shipped.
- **Homebrew, crates.io, release-plz and sccache.** Each adds a moving part
  that a solo maintainer has to keep alive, with little gain at this stage.
