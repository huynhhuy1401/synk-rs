# AGENTS.md

Guidance for AI agents working on this repo. CLAUDE.md points here.

## Commands

```sh
cargo test                     # all unit + CLI integration tests
cargo clippy --all-targets     # must be warning-free
cargo fmt --all
SYNK_E2E_PYTHON=<python with torch + sentence-transformers> cargo test -- --ignored   # real training
```

## CI and releases

- `.github/workflows/ci.yml` builds, lints and tests every push to `main`
  and every PR, on Linux (x86_64, arm64), Windows and Apple Silicon macOS.
- `.github/workflows/release.yml` is generated by [dist](https://opensource.axo.dev/cargo-dist/)
  from `dist-workspace.toml`. Never edit it by hand: change
  `dist-workspace.toml`, run `dist generate`, and check with
  `dist generate --check` and `dist plan`.
- To release: set `version` in `Cargo.toml`, commit, then
  `git tag vX.Y.Z && git push origin vX.Y.Z`. The tag builds the binaries
  and installers and publishes a GitHub release. Only tags run it, not PRs.
- GPUs aren't in CI; test CUDA by hand on a cloud GPU before a release.
- The trainer's Python packages are pinned with hashes in
  `crates/synk-pipeline/locks/` (one file per backend and platform). After
  changing `locks/requirements.in` (or the versions in `sidecar.rs`), run
  `scripts/lock-trainer.sh`, then a real `synk setup`.

## Commits

Use [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/):
`<type>(<optional scope>): <summary>`, lowercase, imperative, no period,
under ~72 characters; details go in the body.

- Types: `feat` (a user-visible feature), `fix` (a bug fix), `docs`,
  `refactor`, `perf`, `test`, `ci`, `build`, `chore`.
- Scopes, when they help: `cli`, `pipeline`, `trainer` (the sidecar),
  `generator`, `store`, `connectors`, `skill`, `ci`, `release`.
- A breaking change to the `--json` contract or `synk.toml`: `feat!:` or
  `fix!:`, plus a `BREAKING CHANGE:` footer saying what to do.
- Examples: `feat(cli): add run list --limit`,
  `fix(trainer): train on one GPU when several are visible`.

## Rules

- **The `--json` output is a public API.** Agents parse it. Don't rename or
  remove fields, `ErrorCode` variants or advice codes; add new ones. Update
  the error and advice tables in README.md when adding a code.
- `next` (in results and errors) must run exactly as written. A fix with a
  placeholder, or one only a person should take, goes in `error.actions`
  (`SynkError::with_action` / `with_hint`). Never give a download or a remote
  send `machine` applicability.
- Name runs and datasets by their readable IDs (`synk_pipeline::ids`) in
  output; keep the raw `key` next to them.
- Hints an agent may act on are `advice` entries (`crates/synk-pipeline/src/advice.rs`)
  with a stable code and an honest `applicability`, not prose in `message`.
- A verdict other than `better` is not an error. Errors mean "couldn't run".
- `--progress jsonl` events go to stderr and carry `v`; stdout is always
  exactly one result object, even for bad arguments.
- Every new command needs a `--json` path, a `next` hint where one makes sense,
  a test in `crates/synk/tests/cli.rs`, and a line in the help template
  (a test checks it). `synk schema` picks it up from clap.
- A new step that spends (downloads, sends text off the machine) must add a
  `Consent` item in `graph.rs`, with a fetch name for downloads that
  `fetch.rs` resolves; `--dry-run` must stay read-only.
- Never add an interactive prompt.
- Connectors only read and normalize. They return a `SyncBatch` of changes and
  never touch the store directly.
- Deleting data means tombstoning (`deleted = 1`), never `DELETE`.
- Edit `synk.toml` only through `Project` in `crates/synk/src/config.rs`
  (`toml_edit`), so user comments survive.
- Everything runs locally. Don't add network calls that send user data
  anywhere without an explicit opt-in config option.
- Never edit a shipped entry in `MIGRATIONS` (`crates/synk-store/src/lib.rs`);
  append a new one.
- Every file contract carries a version: the sidecar protocol
  (`PROTOCOL_VERSION`), dataset JSONL rows (`v`), artifact manifests
  (`schema`), the model catalog (`catalog_version`), progress events (`v`).
  Within a version, only add fields. When a step's output changes for the
  same inputs, bump that step's `KIND_VERSION` (or the generator's
  `PROMPT_VERSION`) so old artifacts aren't reused.
- Downloads and sending text off the machine need consent: running
  `synk fetch` or `synk setup`, or `--yes` (ADR 0002). `train` and `dataset`
  never download by themselves; `--dry-run` never sends document text
  anywhere. No unofficial GPU workarounds (e.g. `HSA_OVERRIDE_GFX_VERSION`).
- Training runs on NVIDIA (CUDA) or CPU only (ADR 0003). Don't add a GPU
  backend nobody has run the end-to-end test on.
- A run's ID is its number (`run:<n>-<label>`); never reuse a number, and
  keep `synk train` idempotent (same inputs return the existing run).
- Use the terms in `GLOSSARY.md`. Decisions live in `docs/adr/`.

## Layout

- `crates/synk-core` — types, `Connector` trait, `ErrorCode`
- `crates/synk-connectors` — one module per source type; `readers.rs` turns
  md/txt/html/docx/pdf bytes into text, or a skip reason
- `crates/synk-store` — SQLite, with append-only migrations
- `crates/synk-pipeline` — the steps and how they run: `graph.rs` (the
  preview: steps, staleness, consent, fetch names), `exec.rs` (runs a
  preview's steps), `fetch.rs` (downloads by name), `ops.rs` (run, dataset
  and fetch records, numbering, lock, heartbeat, cancel), `sync.rs`, `dataset.rs`
  (chunking with `chunk.rs`/`tokenizer.rs`, queries via `generator.rs`, the
  per-query cache), `train.rs` + `stats.rs` (training, eval, the verdict,
  the general check), `export.rs` (st/onnx/gguf + vector check), `hub.rs`
  (Hugging Face cache and metadata), `ids.rs` (readable IDs), `advice.rs`,
  `queries.rs`, `report.rs` / `report_html.rs`, `catalog.toml`, the Python
  trainer (`sidecar.rs` + `sidecar/synk_sidecar.py`, protocol v2, embedded)
  and `fake_trainer.rs` (`SYNK_FAKE_TRAINER=1`, for tests)
- `crates/synk` — CLI: `main.rs` (clap tree and the grouped help template),
  `work.rs` (train, dataset, fetch, wait, logs, cancel), `commands.rs`
  (sources, status),
  `config_cmd.rs`, `pipeline.rs` (setup, models, export, progress), `views.rs`
  (queries, `run ...`), `reference.rs` (`schema`, `skill`),
  `human.rs`, `config.rs`, `output.rs`
- `skills/synk/SKILL.md` — the agent skill for *using* synk; `reference.rs`
  embeds it, `synk skill` emits it (with generated `references/codes.md`)
- `docs/plans/` — accepted plans (`v1-design.md` predates ADR 0002; read it
  through that ADR)

## Agent skills

### Issue tracker

Issues are tracked in GitHub Issues via the `gh` CLI. See `docs/agents/issue-tracker.md`.

### Triage labels

Uses the five default triage labels (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`). See `docs/agents/triage-labels.md`.

### Driving synk

`skills/synk/SKILL.md` — the recipe for *using* the synk CLI as a user
would: the train loop, consent, reading results. Reach it when a task runs
synk commands (it is what `synk skill` emits into user projects), not when
changing synk's code.

### Domain docs

Single-context: one `GLOSSARY.md` and `docs/adr/` at the repo root. See `docs/agents/domain.md`.
